# 功能控制中心 0.0.5 完整系统方案

> 当前补充：1.1.0 已加入由功能脚本主动提交的通用执行结果报表。平台仍不识别商品模型、不解析日志推断状态，也不提供失败项重跑。现行契约、完整性和保留规则见 [`1.1.0-structured-run-reports.md`](./1.1.0-structured-run-reports.md)。

## 1. 文档状态

- 版本：`0.0.5`
- 日期：`2026-09-08`
- 性质：重构方案，不代表当前代码已经实现
- 目标：重新实现现有功能控制中心，同时保留原项目的功能注册方式和业务脚本适配能力
- 交付形态：源代码、Docker 镜像、`docker-compose.yml`、启动脚本、备份恢复工具、使用说明和二次开发说明

本版在 `0.0.4` 的基础上补全五项关键决策：

1. **彻底删除“重新执行失败项”平台能力。** 平台不识别失败商品、不维护失败项清单、不提供失败项重跑按钮或接口。失败处理、网络重试和业务补偿全部属于脚本内部逻辑。
2. **日常可配置项全部进入后台“系统设置”。** 交付包不要求用户编写 `.env`，也不要求用户在启动 Docker 前理解环境变量。首次启动自动生成实例密钥和初始化凭据；系统运行参数通过后台页面维护。
3. **补全功能复制时的数据源初始化规则。** 被复制的客户功能继续共享不可变代码版本，但不共享客户数据源。目标客户会从该功能版本 ZIP 内的默认文件生成自己独立的数据源第 1 版；后续下载、替换和运行都只访问目标客户自己的数据源版本。
4. **明确登录 Token 和会话安全方案。** 浏览器登录采用不可解码的高强度随机会话 Token，通过安全 Cookie 自动传输；服务端只在 SQLite 中保存 Token 摘要和会话状态。首版不使用长期 JWT，也不把 Token 暴露给前端 JavaScript 或 `localStorage`。
5. **明确登录状态持久化。** 会话记录保存在 `/data/fcc.db`，Cookie 使用与服务端绝对有效期一致的持久化期限。浏览器刷新、关闭后重开、容器重启和镜像升级都不会无故丢失登录；备份恢复、域名变更和实例密钥异常等安全边界会要求重新登录。

## 2. 需求边界

### 2.1 平台负责

平台只负责通用的“功能运行管理”：

1. 用户登录、用户管理、客户管理以及用户与客户的多对多关联。
2. 功能包上传、校验、版本记录、启用、停用和复制给其他客户。
3. 为不同客户保存各自的功能配置和数据源文件。
4. 手工运行和定时触发功能。
5. 将功能放到独立子进程中启动，并能请求停止、超时终止和异常回收。
6. 实时接收、保存、展示脚本日志，并在任务结束后提供完整日志下载。
7. 记录操作审计、运行状态和部署实例状态。
8. 备份、恢复和迁移平台数据。

### 2.2 业务脚本负责

以下内容明确不属于平台：

1. Excel、CSV、JSON 或其他数据源的业务字段解释。
2. 商品、店铺、库存、订单等业务对象的定义和唯一键。
3. 判断某个商品是否成功、失败、无数据或需要补偿。
4. 针对失败商品的保存、筛选、重新执行和补偿策略。
5. 网络请求的业务重试策略。脚本可以按自身规则重试一次，平台不重启整个任务。
6. 远端系统是否具有幂等性，以及任务中断后是否需要人工核对。

平台可以可靠保存脚本输出的每一条日志，但不能保证脚本确实为每个商品输出了日志。后者必须由脚本作者实现和测试。

### 2.3 首版明确不做

- 不做“失败项重跑”。
- 不做商品级数据模型和商品级查询页面。
- 不做工作流编排、DAG 或脚本之间的依赖调度。
- 不做插件市场和面向普通用户的功能打包工具。
- 不做高可用、集群调度、Kubernetes、Redis、RabbitMQ、Celery、PostgreSQL、MinIO 或 Elasticsearch。
- 不在运行时遇到 `ModuleNotFoundError` 后修改平台全局 Python 环境。
- 不承诺把不受信任的第三方代码变成安全代码；只有受信任的管理员可以上传可执行功能包。

## 3. 核心设计原则

1. **运行和 Web 请求分离。** Flask 只提交运行请求，不在请求线程或普通后台线程中直接执行脚本。
2. **进程可控。** 每次运行拥有独立子进程、工作目录、进程组和状态记录，因此可以停止并清理。
3. **客户是业务隔离边界。** 功能、配置、数据源、定时任务和运行日志都绑定客户；所有后端接口都校验当前用户是否关联该客户。
4. **平台不理解业务。** 数据源是文件，日志是事件，运行结果是进程结果；平台不猜测商品含义。
5. **一个交付包即可启动。** 不引入必须单独部署的新服务，不要求 `.env`，不要求用户手工安装 Python 依赖。
6. **先保证闭环，再增加扩展点。** 首版只支持一个功能对应零个或一个当前数据源文件，但数据表和 SDK 不把文件格式写死。
7. **安全措施不制造日常负担。** 普通业务人员只看到客户切换、运行、停止、日志、数据源和定时任务；高风险操作集中到后台管理区。
8. **不可恢复的动作必须清楚。** 强制停止可能发生在远端请求已经提交但本地尚未记录结果的时刻，平台只能记录“异常中断”，不能擅自重试。

## 4. 总体架构

### 4.1 单 Docker 应用

交付一个镜像和一个 `docker-compose.yml`。容器内部包含以下长期进程，但对部署人员仍表现为一个应用：

1. **Web/API 进程**：Flask 应用、静态前端、SSE 日志接口、登录和后台管理。
2. **Runner 进程**：领取排队任务、准备工作目录、启动/停止脚本、收集日志和收尾。
3. **Scheduler 进程**：读取 SQLite 中的定时任务，到点只创建运行记录，不直接执行脚本。
4. **Launcher/PID 1**：管理上述进程、转发容器停止信号、回收孤儿进程；任何关键进程反复退出时让容器健康检查失败。

选择单容器不是一般意义上的微服务最佳实践，而是针对本项目低并发、单机、频繁迁移和低运维能力的约束。内部仍保持进程边界，防止 Flask、调度器和业务脚本互相绑死。

### 4.2 代码分层

建议目录：

```text
backend/
  app/
    domain/           # 业务实体、状态机、权限规则，不依赖 Flask
    application/      # 用例：注册功能、发起运行、停止、复制、调度
    infrastructure/   # SQLite、文件物化、加密、依赖环境、备份
    web/              # Flask API、会话、SSE、静态资源
    runner/           # 运行领取、子进程控制、日志采集
    scheduler/        # 数据库驱动的单实例调度循环
    sdk/              # 提供给功能脚本的稳定接口
  migrations/
  tests/
frontend/
  src/
docker/
scripts/
docs/
features/             # 原项目素材，保持原样，不在重构时覆盖
docker-compose.yml
VERSION
README.md
```

依赖方向固定为 `web/runner/scheduler -> application -> domain`，基础设施通过接口注入，禁止页面控制器直接拼 SQL 或直接启动脚本。

## 5. 用户、客户和权限模型

### 5.1 关系

- 一个用户可以关联多个客户。
- 一个客户可以由多个用户管理。
- 一个客户可以注册多个功能。
- 同一个功能版本可以被多个客户复用，但配置、数据源、定时任务和日志互相独立。

这不是复杂的强租户 SaaS。实现上使用 `customer_id` 作为业务归属标记，并在服务端统一做客户访问校验。

### 5.2 首版角色

为了避免细粒度权限造成维护负担，首版只保留两个角色：

| 角色 | 能力 |
| --- | --- |
| 系统管理员 | 用户、客户、关联关系、功能上传/版本、功能复制、系统设置、配置管理、全部客户业务操作 |
| 业务操作员 | 仅在已关联客户内查看功能、替换/下载数据源、运行/停止、查看日志、维护定时任务 |

配置管理涉及密钥，首版只允许系统管理员访问。将来如果确实存在“业务人员必须改非密钥配置”的场景，再增加配置管理员角色，当前数据结构预留角色扩展但不提前做复杂授权界面。

### 5.3 客户切换

前端左上角始终显示当前客户。切换客户后重新加载该客户的功能、配置权限、日志和定时任务。后端不信任前端保存的客户 ID，每个请求都重新验证 `user_customer` 关系，避免通过改 URL 或请求体越权访问其他客户。

## 6. 功能模型和快捷复制

### 6.1 三层模型

1. `feature_definition`：功能的稳定身份，例如“Ozon 库存同步”。
2. `feature_version`：某次上传的不可变代码版本、元数据、依赖锁和状态。
3. `customer_feature`：某客户启用该功能的注册记录，指向一个已就绪版本。

这样设计的原因是：上传一次代码后，复制给 100 个客户只新增 100 条客户关联记录，不复制 ZIP，不重复安装依赖，也不把 A 客户的配置和数据混到 B 客户。

### 6.2 快捷复制规则

管理员在一个已有客户功能上选择“复制到其他客户”，可以一次勾选多个目标客户。

默认复制：

- 功能定义和当前版本引用；
- 功能展示名称、说明和配置结构；
- 非敏感配置的默认值；
- 如果当前功能版本携带默认数据源，则以该默认文件为每个目标客户分别创建一条独立的数据源第 1 版。

默认不复制：

- 历史运行和日志；
- 定时任务；
- 已填写的配置值，尤其是密钥；
- 来源客户当前使用的数据源文件和它的历史版本。

被复制功能的代码仍然引用同一个不可变 `feature_version`，但是每个目标客户都有自己的 `customer_feature` 和数据源版本链。目标客户初始数据源的字节来自 `feature_version` 中登记的默认文件，而不是来自来源客户当前使用的文件。复制完成后，目标客户点击“下载数据源”得到的就是自己的当前数据源；在尚未替换前，它与功能包默认文件内容一致。

首版不提供“同时复制来源客户当前数据源”选项。原因是这个操作很容易把 A 客户的商品或店铺数据带给 B 客户，而且甲方已经明确复制后的初始文件应来自功能包默认文件。如果以后出现确定的跨客户复制数据需求，应作为单独的、有明确提示和审计的导入操作设计，不能混入普通功能复制。

如果功能版本声明数据源为必需但 ZIP 未携带默认文件，目标客户功能仍可创建，但状态为 `WAITING_DATA_SOURCE`，在目标客户上传文件之前禁止运行。如果数据源不是必需项，则允许没有初始文件。

复制过程使用数据库事务：某个目标客户失败时返回逐客户结果，不产生半条关联记录。

## 7. 功能包协议

### 7.1 包结构

正常开发者只需要写脚本、`__meta__` 和可选的 `requirements.txt`，不要求每次额外运行打包工具：

```text
ozon_inventory.zip
  __init__.py
  ozon.py
  requirements.txt       # 可选；声明新增 Python 依赖
  dataSource.xlsx        # 可选；注册时的默认数据源
```

离线环境需要从未安装过的新依赖时，可以额外携带：

```text
  wheels/                # 可选；离线 wheel 文件
```

### 7.2 元数据

继续兼容原项目的 `__meta__`，但注册时只用 AST 读取字面量，不导入或执行功能代码：

```python
__meta__ = {
    "name": "Ozon 库存同步",
    "description": "按客户数据源同步库存",
    "entrypoint": "run",
    "configs": {
        "api_key": {
            "type": "secret",
            "required": True,
            "description": "Ozon API Key",
        },
        "timeout_seconds": {
            "type": "integer",
            "default": 30,
            "min": 1,
            "max": 300,
        },
    },
    "data_source": {
        "filename": "dataSource.xlsx",
        "required": True,
        "extensions": [".xlsx"],
        "description": "库存同步数据源",
    },
}
```

`customer` 不再由 ZIP 元数据决定。客户归属必须来自管理员在平台中的操作，否则复制功能和权限边界会失真。

### 7.3 注册安全和状态

- 只允许系统管理员在受保护的管理区上传功能包。
- ZIP 条目必须经过路径规范化，拒绝绝对路径、`..`、符号链接、重复冲突路径和异常解压比例。
- 限制包大小、条目数和单条目大小，具体阈值在后台“系统设置”中维护。
- 注册阶段不执行 `__init__.py`。
- 功能版本状态为 `PREPARING`、`READY` 或 `DEPENDENCY_FAILED`；只有 `READY` 可以运行。
- 新版本准备失败不影响当前正在使用的旧版本。

## 8. Python 依赖管理

### 8.1 日常路径

Docker 镜像只包含平台依赖、SDK 和现有旧脚本所需的基础兼容依赖。新功能有新依赖时：

1. 开发者在 ZIP 中放普通 `requirements.txt`。
2. 管理员上传 ZIP 后，平台自动进入“准备运行环境”。
3. 平台解析依赖，在独立构建目录下载并安装，不修改平台全局 Python。
4. 运行 `pip check` 并做最小导入检查；成功后版本变为 `READY`。
5. 平台保存最终解析的精确版本和哈希，恢复部署时可以重建同一环境。

普通用户、客户数量和依赖安装次数没有直接关系。

### 8.2 自动复用

运行环境按以下指纹复用：

```text
Python 主次版本 + 规范化后的精确依赖集合 + wheel 哈希
```

- 相同依赖组合只准备一次。
- 同一功能复制给多个客户不重新安装。
- 功能代码升级但依赖未变时复用原环境。
- wheel 缓存放在 `/data/runtime-cache/wheels`，属于可重建缓存，不是业务真源。

### 8.3 离线和系统级依赖

- 服务器能联网时，缺失 wheel 自动下载一次。
- 服务器完全离线且缓存中没有新依赖时，ZIP 可以携带 `wheels/`；可选打包工具只是帮助开发者准备这些 wheel，不是日常必经步骤。
- Chrome、Playwright 浏览器、Java、FFmpeg、ODBC 驱动、系统字体和原生动态库属于操作系统级依赖，必须发布新 Docker 镜像，不能假装由 Python 功能包安全解决。

依赖源、超时、离线模式和缓存上限放到后台“系统设置”，不要求环境变量。

## 9. 数据源文件机制

### 9.1 归属和行为

数据源归属于 `customer_feature`：A 客户的 Ozon 功能和 B 客户的 Ozon 功能拥有各自独立的版本链。它们可以引用同一个功能代码版本，但不会引用同一条客户数据源记录。

首版每个客户功能支持零个或一个“当前数据源指针”，后台允许存在多个不可变数据源版本。页面只提供：

- 查看文件名、大小、SHA-256、上传者和更新时间；
- 下载当前文件；
- 上传新文件并原子替换当前文件。

平台不打开表格、不读取工作表、不判断列名、不统计商品、不修改内容。它只按元数据检查是否必需、允许的扩展名、非空、大小上限和哈希。

### 9.2 两类数据源记录

系统明确区分：

1. **功能版本默认数据源**：属于 `feature_version`，来自 ZIP，只读且不可被客户上传覆盖。
2. **客户功能数据源版本**：属于 `customer_feature`，每次初始化或替换都会产生一条新的不可变版本。

推荐的数据关系：

```text
feature_version
  └── feature_version_default_data_source（零或一条）

customer_feature
  ├── current_data_source_revision_id
  └── customer_feature_data_source_revision（零到多条）
```

即使多个客户的初始文件字节完全相同，也要为每个客户创建独立的数据源版本记录。首版业务量很小，直接复制约 1 MB 的默认文件比引入跨客户内容去重和引用计数更简单，也更不容易发生授权错误。SHA-256 仍用于完整性校验，不用作跨客户授权依据。

### 9.3 注册和复制时的初始化

功能包可以携带元数据声明的默认文件。上传功能版本时，平台将默认文件从 ZIP 中安全读取并登记为该 `feature_version` 的只读默认数据源。

首次注册或复制给客户时：

1. 创建目标客户自己的 `customer_feature`。
2. 如果功能版本存在默认数据源，复制其内容并创建目标客户的数据源第 1 版。
3. 将目标 `customer_feature.current_data_source_revision_id` 指向该第 1 版。
4. 目标客户下载数据源时，只通过自己的 `customer_feature` 权限读取这条记录。

因此，“共享代码”和“隔离数据源”同时成立：代码 ZIP 不重复，客户数据源各自存储、各自更新。后续替换只影响当前客户，不修改功能版本默认文件，也不影响其他客户。

### 9.4 替换和运行快照

用户上传替换文件时不覆盖旧 BLOB，而是创建该客户的数据源第 2、3、4 版，再原子更新当前指针。首版前台只展示当前版本，不增加复杂的历史版本管理页面；保留旧版本是为了保证已经创建的运行快照仍可重现。

创建运行请求时，将当时的 `customer_feature_data_source_revision_id` 写入运行记录。即使用户随后替换文件，已经排队或正在运行的任务仍使用发起时的版本。

Runner 不让业务脚本读取平台内部存储路径。它根据运行快照取出对应客户的数据源内容，物化到本次独立工作目录，并使用当前功能版本元数据中的原文件名。这样旧脚本仍可通过 `os.path.join(os.path.dirname(__file__), "dataSource.xlsx")` 读取；新脚本推荐使用 SDK：

```python
data_source_path = ctx.get_data_source_path()
```

示例：

```text
平台内部记录：
  A客户 / Ozon / 数据源v3
  B客户 / Ozon / 数据源v1（来自功能包默认文件）

运行时临时路径：
  /data/tmp/<A的request_id>/feature/dataSource.xlsx
  /data/tmp/<B的request_id>/feature/dataSource.xlsx
```

脚本看到的文件名可以相同，但文件内容由 `request_id` 对应的数据源快照决定，客户之间不会共用运行目录。

### 9.5 功能代码升级时的数据源规则

功能版本从 V1 升级到 V2 时，平台不能自动用 V2 包内默认文件覆盖客户已经维护的数据源。默认行为是保留客户当前数据源。

- 新复制或新注册的客户使用 V2 的默认数据源创建自己的第 1 版。
- 已有客户升级代码时保留其当前数据源。
- 如果 V2 的元数据不再接受当前文件扩展名，升级必须暂停，要求管理员选择“使用 V2 默认文件”或为该客户上传新文件。
- 选择“使用当前功能版本默认文件”时，也不是直接共享默认记录，而是为该客户创建一个新的数据源版本并切换当前指针。

平台只判断元数据声明的文件名、必需性和扩展名，不判断 Excel 内容是否与新代码在业务上兼容；这一点仍由脚本作者和升级说明负责。

## 10. 配置管理

### 10.1 功能配置

- 配置结构来自当前功能版本的 `__meta__["configs"]`。
- 配置值归属于 `customer_feature`，不同客户完全独立。
- 支持字符串、整数、小数、布尔、枚举、普通长文本和密钥类型。
- 保存前由后端按配置结构验证；前端验证只用于改善体验。
- 运行创建时保存加密配置快照，避免任务排队期间配置改变导致行为不确定。

### 10.2 密钥配置

- 密钥使用实例密钥加密后存入 SQLite。
- 实例密钥首次启动自动生成在 `/data/instance.key`，不由用户配置环境变量。
- API 和页面不返回密钥明文，只显示“已设置”；修改时执行替换，而不是提供普通查看按钮。
- 修改密钥要求再次输入当前登录密码，并写入审计日志。

### 10.3 配置管理额外访问门

后台“系统设置”提供管理区网络保护：

1. `仅账号权限`：只做登录、角色和 CSRF 校验。
2. `仅可信网络`：在账号权限之外，再要求客户端地址属于管理员维护的可信 CIDR。

系统不能可靠地“自动判断公司内网”。公网服务器通常只能看到公司出口公网 IP，反向代理还可能改变来源地址。因此不写死 `192.168.0.0/16` 等网段，而是：

- 在页面显示当前请求实际解析到的 IP，并可一键建议 `/32`；
- 允许管理员填写公司 LAN、VPN 或固定出口公网 CIDR；
- 只有来源地址属于已登记的可信反向代理时，才读取 `X-Forwarded-For`；否则完全忽略该请求头；
- 启用前做“当前连接仍可访问”检查，避免自己锁死；
- 已启用后，修改网络规则必须来自现有可信网络并再次验证密码。

受网络门保护的管理区至少包括：

- 功能配置；
- 功能包上传、升级和删除；
- 用户、客户和关联关系管理；
- 系统设置和备份恢复。

普通运行、停止、日志、数据源和定时任务仍可在公网入口由已授权用户操作。网络限制是凭据泄露后的第二道门，不等于服务器被远程执行代码后还能保护数据库。

## 11. 运行调度和停止机制

### 11.1 创建运行

手工运行或定时触发最终都只执行同一个应用用例：

1. 校验用户、客户、功能启用状态、功能版本、必需配置和必需数据源。
2. 生成全局唯一 `request_id`。
3. 固化功能版本、配置快照和数据源快照。
4. 在 SQLite 中新增 `QUEUED` 运行记录并立即返回。
5. 前端打开实时日志页面；Runner 在后台领取任务。

### 11.2 Runner 领取

Runner 通过短事务原子领取任务，避免同一任务被重复启动。默认：

- 全局并发数为 `2`，可在后台调整；
- 同一 `customer_feature` 同时只运行 `1` 个实例；
- 最大运行时长默认“不限制”，可在单个功能上设置；
- 定时触发遇到同功能仍在运行时默认跳过并记录日志，不累计无限队列。

选择保守默认值是因为实际并发和最长时长尚不明确。上线后的运行记录可以支持再调整，而不是一开始引入复杂队列系统。

### 11.3 子进程启动

每次运行创建独立临时目录，包含：

- 当前不可变功能版本；
- 本次数据源快照；
- 仅本任务可读的临时配置文件；
- SDK 启动器。

Runner 用对应的隔离 Python 环境启动脚本，设置独立进程组，清理无关环境变量，限制可访问工作目录，并捕获标准输出、标准错误和 SDK 事件。脚本进程不能读取平台 SQLite、实例密钥或其他客户工作目录。

业务同步脚本必须联网，因此首版不能完全禁用网络。可执行功能包仍被视为受信任代码，上传权限必须严格控制。

### 11.4 停止

停止不是杀 Flask 线程，而是两阶段控制脚本进程组：

1. 页面点击停止后，运行状态变为 `STOPPING`，Runner 向进程组发送 `SIGTERM`。
2. 新脚本可以周期性调用 `ctx.raise_if_cancelled()` 做友好收尾。
3. 超过后台配置的宽限时间仍未退出时，Runner 发送 `SIGKILL`。
4. Runner 读取并写完管道中剩余日志后，再把任务封存为 `STOPPED`。

强制停止无法撤销已经发到第三方平台的请求。平台不会自动再跑一次；日志中会清楚记录停止方式、时间和退出码，业务人员是否补偿由脚本和业务流程决定。

### 11.5 容器异常重启

Runner 周期性写心跳。容器启动时发现仍为 `STARTING`、`RUNNING` 或 `STOPPING` 且没有活跃进程的记录，将其标记为 `INTERRUPTED`，保留已有日志，不自动恢复、不自动重试。

## 12. 脚本 SDK

新功能推荐入口：

```python
def run(ctx):
    ctx.log.info("开始同步")
    source_path = ctx.get_data_source_path()
    api_key = ctx.config.get_secret("api_key")

    for row in read_business_rows(source_path):
        ctx.raise_if_cancelled()
        sync_one_row(row, api_key)
        ctx.log.info("商品处理完成", extra={"sku": row.sku})
```

SDK 首版只提供：

- `ctx.request_id`
- `ctx.customer_id`
- `ctx.feature_id`
- `ctx.config.get(...)`
- `ctx.config.get_secret(...)`
- `ctx.get_data_source_path()`
- `ctx.log.debug/info/warning/error(...)`
- `ctx.raise_if_cancelled()`

兼容适配器继续支持原项目的 `run(configs, ctx)`。SDK **不提供** `failed_items`、`retry_failed_items` 或商品状态接口，避免平台越过通用运行边界。

## 13. 实时日志和最终日志

### 13.1 采集

Runner 同时采集：

- SDK 结构化日志；
- `stdout`；
- `stderr`；
- 平台生命周期事件，例如领取、启动、停止信号、强制终止和退出码。

每条事件具有 `request_id`、递增序号、时间、级别、来源和消息，可附带脚本自己提供的 JSON 上下文。平台把上下文当作日志字段保存，不将其解释为商品记录。

### 13.2 持久化和实时传输

- Runner 小批量写入 SQLite，避免每行单独提交造成锁竞争。
- 前端通过 SSE 接收增量日志；不额外引入 WebSocket 服务。
- SSE 使用事件序号和 `Last-Event-ID`，浏览器刷新或短暂断网后补发缺失日志。
- 页面点击“运行”后直接进入本次 `request_id` 的日志抽屉；离开页面不影响任务，返回后可继续读取。

### 13.3 最终封存

进程退出后，Runner 先排空输出管道并提交最后一批日志，再写结束状态、退出码和结束时间。只有这一步成功后，运行才显示为终态。

日志详情页支持下载完整 `.log` 和 `.jsonl`。下载内容由已封存的 `run_event` 生成，避免另存一份不同步的“最终日志”。如果脚本没有为某个商品输出日志，平台不会伪造记录。

### 13.4 日志查询

查询条件保持简单：

- 客户；
- 功能；
- 运行状态；
- 手工/定时；
- 时间范围；
- `request_id`。

不建设商品级搜索引擎。日志正文搜索首版不做，避免把 SQLite 变成全文检索平台。

## 14. 定时任务

- 定时任务归属于 `customer_feature`。
- 页面提供常用的每天、每周、每月配置，保留高级 Cron 输入。
- 时区来自后台系统设置，页面始终显示下一次触发的本地时间。
- Scheduler 是唯一调度进程，只创建 `run`，不启动脚本。
- `run.trigger_key` 对“定时任务 ID + 计划触发时间”建立唯一约束，容器重启后也不会重复创建同一次触发。
- 禁用客户、禁用功能或版本未就绪时不执行，记录原因。
- 不自动补跑容器离线期间错过的历史批次，避免一次恢复后集中触发未知数量的业务请求；页面显示“错过触发”。

## 15. 数据模型

首版核心表：

| 表 | 责任 |
| --- | --- |
| `user` | 账号、Argon2id 密码哈希、角色、状态、安全版本、强制改密标记 |
| `customer` | 客户基本信息和状态 |
| `user_customer` | 用户与客户多对多关系 |
| `session` | 登录 Token 摘要、用户、安全版本、CSRF 密钥、闲置/绝对过期时间和吊销状态 |
| `feature_definition` | 功能稳定身份 |
| `feature_version` | 不可变 ZIP、元数据、依赖锁、准备状态 |
| `feature_version_default_data_source` | 某功能版本 ZIP 中登记的只读默认数据源，零或一条 |
| `runtime_environment` | 依赖指纹、Python 版本、缓存路径和状态 |
| `customer_feature` | 客户注册的功能和当前版本 |
| `feature_config_value` | 客户功能当前配置，密钥字段加密 |
| `customer_feature_data_source_revision` | 某客户功能的不可变数据源版本、来源版本、文件名、哈希、上传人 |
| `scheduled_task` | 定时规则、状态和下一次时间 |
| `run` | `request_id`、快照、触发来源、状态、退出信息、停止请求 |

| `runner_heartbeat` | Runner 活性和异常恢复判断 |

- `user_customer(user_id, customer_id)` 唯一；
- `customer_feature(customer_id, feature_definition_id)` 唯一；
- `run(request_id)` 唯一；
- `run(trigger_key)` 在非空时唯一；
- `run_event(run_id, sequence)` 唯一；
- 所有客户业务查询必须同时带 `customer_id` 授权条件。

## 16. SQLite、文件和备份

### 16.1 SQLite 使用方式

- 一个本机 SQLite 数据库 `/data/fcc.db` 作为业务真源。
- 功能 ZIP、数据源文件、配置、运行记录和日志保存在数据库中，方便迁移。
- 启用外键、WAL、`busy_timeout` 和短事务；日志批量写入。
- 数据库必须位于 Docker 主机本地磁盘，不放在 SMB/NFS 网络共享上。
- 镜像固定使用包含 SQLite `3.51.3` 或更高修复版本的运行时。

### 16.2 `/data` 目录

```text
data/
  fcc.db                 # 业务数据库
  instance.key           # 自动生成的实例加密密钥
  runtime-cache/         # 可重建的 Python 环境和 wheel 缓存
  tmp/                   # 可清理的运行工作目录
```

`docker-compose.yml` 默认把交付目录下的 `./data` 绑定到 `/data`。重新部署时复制该目录即可；真正不可替代的是 `fcc.db` 和 `instance.key`，缓存丢失后可以按锁文件重建。

### 16.3 后台备份

系统设置提供“创建备份”和“下载备份”：

- 使用 SQLite Online Backup API 生成一致性快照，而不是运行中直接复制数据库文件；
- 将数据库、实例密钥、版本清单和校验文件放入一个加密的 `.fccbackup`；
- 备份密码由管理员当次输入，不存进数据库；
- 恢复只允许在首次启动向导或本机恢复命令执行，并先校验版本和哈希。

运行环境不直接备份为可搬运虚拟环境，因为 Python 虚拟环境不保证可移动；保存依赖锁和 wheel 后重建更可靠。

## 17. 系统设置与零环境变量启动

### 17.1 结论

交付包中**没有必须由甲方维护的 `.env`**。以下设置全部在后台页面和 `system_setting` 中管理：

- 系统名称、时区、会话时长；
- 全局并发数、停止宽限时间、默认超时；
- 日志保留天数和数据库容量告警阈值；
- 功能包/数据源大小限制；
- Python 依赖源、下载超时、离线模式和缓存上限；
- 管理区网络保护、可信 CIDR 和可信反向代理；
- 登录限速和密码策略中的可调参数。

修改敏感系统设置需要管理员重新验证密码并写审计。Runner 和 Scheduler 定期读取设置版本，绝大部分配置无需重启容器。

### 17.2 自动生成内容

首次启动自动完成：

1. 创建 `/data` 子目录和 SQLite 表。
2. 生成高强度实例密钥并写入 `/data/instance.key`。
3. 生成一次性初始化码，写入宿主机可见的 `data/first-run.txt`。
4. 用户打开页面，输入初始化码并创建第一个管理员。
5. 成功后初始化码立即失效，`first-run.txt` 自动删除。

这避免交付包内置默认密码，也避免公开服务器出现“谁先打开页面谁成为管理员”的风险。

### 17.3 固定的部署级事实

应用内部端口、`/data` 路径和容器启动命令直接写在镜像与 `docker-compose.yml` 中，不作为用户日常配置。默认启动命令只有：

```bash
docker compose up -d
```

Windows 交付包额外提供双击可用的 `start.bat`，Linux 提供 `start.sh`；它们只是执行同一条 Compose 命令并显示访问地址和首次初始化文件位置，不形成第二套配置。

公网 TLS、域名和路由器端口映射属于部署网络边界。系统无需这些配置也能当场启动；对公网开放时必须接入甲方已有 HTTPS 入口或反向代理，不能用 HTTP 直接暴露登录和配置。

## 18. 安全方案

### 18.1 登录凭据

- 禁止公开注册，账号只能由系统管理员创建。
- 管理员创建普通用户时生成一次性临时密码，用户首次登录必须修改；临时密码不能由管理员再次查看。
- 密码使用 Argon2id 保存，哈希参数随密码哈希一同存储；登录成功时发现参数落后则自动重新哈希。
- 首版密码最少 12 个字符，允许粘贴和密码管理器，不设置无意义的定期强制改密，不使用安全问题找回密码。
- 普通用户忘记密码时由管理员重置；密码被重置后，用户的所有现有会话立即失效。
- 登录错误统一返回“账号或密码错误”，不向外部确认某个账号是否存在。

### 18.2 为什么不用长期 JWT

浏览器当然需要一个登录 Token，但 Token 不等于必须使用 JWT。本系统是单机、同源前后端、SQLite 始终可用，而且用户角色、启停状态和客户关联必须能够立即生效。使用长期 JWT 会带来：

- 用户被停用后，已经签发的 JWT 在到期前仍可能有效；
- 修改用户角色或移除客户关联后，需要额外黑名单或缩短有效期；
- 为保持登录又要增加 Refresh Token、轮换和撤销机制；
- 把 Token 交给 JavaScript 或 `localStorage` 会扩大 XSS 窃取范围。

因此首版使用**服务端不透明会话**：浏览器只持有一个没有业务含义的随机 Token，用户、角色、客户权限、有效期和吊销状态都保存在服务器。这样退出登录、停用账号、修改密码和强制下线可以立即生效。

JWT 只在未来确实出现无状态外部 API 或多服务验证需求时重新评估，不能因为旧系统用了 JWT 就继续沿用。

### 18.3 登录 Token 生成和保存

登录成功后：

1. 使用操作系统密码学安全随机源生成 32 字节、即 256 位随机值。
2. 将随机值编码为 URL 安全 Token，Token 本身不包含用户 ID、角色、客户列表或到期时间。
3. 使用从 `/data/instance.key` 派生的会话摘要密钥计算 Token 的 HMAC-SHA-256。
4. SQLite 的 `session` 表只保存摘要，不保存浏览器拿到的原始 Token。
5. 原始 Token 只通过 Cookie 返回一次，任何应用日志、审计日志和错误日志都禁止记录它。

数据库泄露时，攻击者不能直接把 `session.token_digest` 当成浏览器 Token 使用。因为原始 Token 具有足够随机性，也不能通过普通字典攻击反推。

建议的 `session` 字段：

```text
id
token_digest
user_id
user_security_version
csrf_secret
created_at
last_seen_at
idle_expires_at
absolute_expires_at
reauthenticated_at
revoked_at
revoked_reason
created_ip
user_agent_hash
```

IP 和 User-Agent 用于审计和异常提示，不做僵硬的逐请求强绑定，避免公司出口切换或浏览器升级导致普通用户频繁掉线。

### 18.4 Cookie 传输

公网 HTTPS 模式使用：

```http
Set-Cookie: __Host-fcc_session=<opaque-token>;
            Secure;
            HttpOnly;
            SameSite=Lax;
            Path=/;
            Max-Age=86400;
            Expires=<absolute-expiry-gmt>
```

规则：

- 不设置 `Domain`，Cookie 只属于当前主机。
- `HttpOnly` 阻止前端 JavaScript 直接读取 Token。
- `Secure` 保证 Token 只通过 HTTPS 发送。
- `SameSite=Lax` 降低跨站请求携带 Cookie 的范围，同时不破坏用户从普通链接进入系统。
- `Max-Age` 和 `Expires` 不超过服务端绝对有效期，使浏览器关闭后重开仍可继续会话；服务端过期时间始终是最终依据。
- 浏览器 API 只接受 Cookie 中的会话 Token；拒绝 URL 参数、查询字符串和普通表单字段中的会话 Token。
- 前端不保存 Token 到 `localStorage`、`sessionStorage`、Pinia 或 Redux 持久化状态。

直接启动时允许局域网 HTTP 完成初始化和内网使用，但页面会明确标记“非安全连接”。首次向导提供 `局域网 HTTP` 和 `公网 HTTPS` 两种部署模式；对公网开放必须选择 HTTPS 模式。HTTPS 模式下，系统拒绝在非加密请求上建立登录会话，并在确认代理配置正确后启用 HSTS。

系统只有在请求确实来自后台登记的可信反向代理时，才采用转发的协议和客户端地址，不能让外部请求通过伪造 `X-Forwarded-Proto: https` 获得安全 Cookie 判断。

### 18.5 登录状态如何持久化

不透明会话并不等于内存会话。登录状态由两个持久化部分共同组成：

1. 浏览器保存有明确 `Max-Age/Expires` 的安全 Cookie；
2. 服务端把会话摘要、有效期和吊销状态保存在持久化卷中的 `/data/fcc.db`。

因此以下操作不会要求用户重新登录，只要会话仍在闲置和绝对有效期内：

- 刷新页面；
- 在系统页面之间跳转；
- 切换客户；
- 关闭浏览器后重新打开；
- Flask/Runner/Scheduler 进程重启；
- Docker 容器正常重启；
- 更新镜像但继续挂载原来的 `./data:/data`。

前端启动后不从本地存储读取 Token，而是调用 `GET /api/me`。浏览器自动携带 HttpOnly Cookie；服务端验证成功后返回当前用户、角色和已授权客户，前端据此恢复界面。最后一次选择的客户可以作为非敏感界面偏好保存，但后端仍重新校验授权。

以下情况有意要求重新登录：

- 会话闲置或绝对过期；
- 用户主动退出；
- 管理员强制下线；
- 用户停用、密码重置或角色改变；
- 系统从备份恢复后统一吊销备份内会话；
- 迁移后访问域名改变，原域名 Cookie 按浏览器安全规则不会发送给新域名；
- `instance.key` 不匹配现有数据库。

如果发现已有 `fcc.db` 但 `/data/instance.key` 缺失或不匹配，系统不能自动生成新密钥后继续运行，而应进入安全故障状态并要求恢复正确密钥。否则不仅登录状态会失效，已加密的功能密钥配置也无法可靠解密。

SQLite 按 `token_digest` 建立唯一索引。当前规模下每个请求进行一次索引查询成本很低，而且避免 Redis 和内存会话造成的部署负担。过期会话由后台维护任务分批清理，不影响审计日志。

### 18.6 会话校验和权限实时生效

每个需要登录的请求都执行：

1. 读取 Cookie 中的原始 Token。
2. 计算 Token 摘要并查询 `session`。
3. 检查会话未吊销、未闲置过期、未绝对过期。
4. 检查用户仍然启用。
5. 比较 `session.user_security_version` 和 `user.security_version`。
6. 从数据库读取当前角色和用户客户关联，不相信 Token 中携带的旧权限。
7. 对指定 `customer_id` 再执行一次 `user_customer` 校验。

密码变更、密码重置、角色变更和用户停用会递增 `user.security_version` 并吊销现有会话。移除客户关联则通过每请求数据库授权立即生效，不必等登录 Token 过期。

为了减少 SQLite 写入，`last_seen_at` 最多每 5 分钟更新一次，而不是每个请求写一次。

### 18.7 会话时限和强制下线

推荐默认值：

- 闲置超时：8 小时；
- 绝对有效期：24 小时；
- 敏感操作重新认证有效期：10 分钟；
- 单用户同时登录设备数：5 个，超出后吊销最旧会话。

这个默认值允许业务人员在一个工作日内正常使用、刷新和重开浏览器而不重复登录，同时要求至少每天重新认证一次。参数可以在后台系统设置中调整，但代码保留合理的最小值和最大值，防止误设成永久会话。首版不提供“永久记住我”。

退出登录时同时：

- 服务端把会话标记为已吊销；
- 浏览器 Cookie 立即过期；
- 返回 `Clear-Site-Data` 清理可清理的认证相关缓存；
- 前端清空当前用户和客户上下文。

用户管理页为管理员提供“强制下线全部设备”，不要求管理员接触 Token。

### 18.8 CSRF 和前端安全

Cookie 会自动随请求发送，因此所有修改状态的 API 必须有独立 CSRF 防护：

- 登录页先从 `GET /api/auth/csrf` 获取短期预登录 CSRF Token；
- 登录后的 CSRF Token 与服务端会话绑定；
- `POST`、`PUT`、`PATCH`、`DELETE` 必须在 `X-CSRF-Token` 请求头携带正确值；
- 敏感接口额外验证 `Origin`，不把 `SameSite` 当成 CSRF Token 的替代品；
- SSE 和普通查询是只读请求，但仍需要有效会话和客户授权。

日志消息、功能说明和脚本输出全部视为不可信文本。前端使用文本节点展示，不允许直接 `v-html` 渲染；平台过滤终端控制字符并限制单条日志长度。页面设置严格 CSP、点击劫持、MIME 嗅探和合理的 Referrer Policy。

### 18.9 登录防爆破

- 登录失败同时按账号标识和解析后的客户端 IP 计数。
- 使用分级冷却时间，不做永久账号锁定，防止攻击者通过反复尝试把正常账号长期锁死。
- 登录成功后清理对应的短期失败窗口，但保留审计事件。
- 不默认增加图片验证码或短信验证码，避免引入外部服务和给普通用户增加操作负担。
- 管理员登录、失败次数异常和管理区拒绝访问均写审计日志，但不记录密码、原始 Token、CSRF Token 或完整密钥。

### 18.10 敏感操作重新认证

即使已有有效会话，以下操作仍要求再次输入当前密码：

- 修改功能密钥配置；
- 修改可信网络和可信代理；
- 上传或启用可执行功能版本；
- 创建或恢复备份；
- 修改用户角色；
- 重置其他用户密码；
- 关闭管理区网络保护。

重新认证成功只在当前会话内记录 10 分钟有效状态，不签发第二种长期 Token，不影响普通运行、查看日志和切换客户。

### 18.11 多因素认证边界

首版不强制普通业务操作员使用短信或扫码验证，以免引入账号找回和外部服务维护成本。数据模型为管理员 TOTP 多因素认证预留扩展位，但在甲方明确能承担恢复码和换手机支持流程之前，不把半成品 MFA 当作安全卖点。

当前安全叠加方式是：管理员角色、可信网络门、敏感操作重新认证、会话即时吊销和审计；普通用户仍然只需正常登录和操作。

### 18.12 API Token 边界

首版没有第三方调用平台 API 的需求，因此不创建个人访问 Token。将来如果需要外部系统调用，应单独设计具有作用域、到期时间、摘要存储和独立吊销能力的 API Token，不能复用浏览器登录 Cookie，也不能把用户密码交给脚本。

### 18.13 授权

- 每个接口显式声明角色要求和客户访问要求。
- 下载数据源、下载日志、SSE 连接、停止任务同样执行服务端授权，不认为“只读接口”天然安全。
- 客户和用户只做停用，不硬删除已有历史关系。
- 高风险操作全部进入审计日志，审计日志不记录密钥明文。

### 18.14 上传和脚本

- 数据源上传只做通用安全检查，不增加杀毒服务、内容净化系统或对象存储。
- 功能包上传风险远高于数据源，因为它是可执行代码，所以只允许受保护管理区的系统管理员操作。
- Runner 以受控子进程启动功能，脚本使用低权限执行用户；平台数据库、实例密钥和其他任务目录不向脚本用户开放。
- 日志输出做长度限制和控制字符处理，防止恶意日志破坏终端或页面。
- 平台不会声称同容器执行任意恶意脚本能够达到强沙箱效果。需要运行不受信任代码时，应改为外部隔离执行器，这不属于当前范围。

### 18.15 应急恢复

如果管理员误配可信网络导致无法进入管理区，提供仅能在 Docker 主机执行的应急命令：

```bash
docker compose exec app fccctl admin-access reset
```

这是非常用恢复手段，不要求日常维护环境变量，也不能通过公网 API 调用。

## 21. 状态机

运行状态：

```text
QUEUED -> STARTING -> RUNNING -> SUCCEEDED
                              -> FAILED
                              -> STOPPING -> STOPPED
                              -> TIMED_OUT
                              -> INTERRUPTED
```

规则：

- 只有 Runner 可以把任务置为 `STARTING/RUNNING/终态`。
- Web 只能创建 `QUEUED` 和设置 `stop_requested_at`。
- 终态不可回退或再次运行；再次点击运行必须创建新的 `request_id`。
- `SUCCEEDED` 只代表脚本进程按协议正常退出，不代表平台验证了每个商品的业务结果。
- `FAILED` 只代表本次功能进程失败，不生成平台失败项清单。

## 24. 验收标准

1. 新机器不创建 `.env`，执行 `docker compose up -d` 后能完成首次初始化并登录。
2. 一个用户可以关联多个客户；切换客户后看不到未关联客户的数据。
3. A、B 客户使用同一功能版本时，代码可以共享，配置和客户数据源版本互不影响。
4. 功能包有新 Python 依赖时上传后自动准备；相同依赖和跨客户复制不重复安装。
5. 点击运行立即获得 `request_id` 并打开日志，日志持续刷新；刷新浏览器不会丢失已保存日志。
6. 点击停止后先友好终止，超时后强制终止；Flask 服务仍正常响应。
7. 容器重启不会自动重跑异常中断的业务任务，已有日志可查。
8. 任务结束后能下载与数据库事件一致的完整日志。
9. 平台没有失败项模型、失败商品页面或失败项重跑接口；脚本失败补偿完全由脚本处理。
10. 数据源可以下载和替换；每次替换创建新的客户数据源版本，运行使用创建请求时的文件快照。
11. 功能可一次复制给多个客户；代码版本共享，但每个目标客户都从包内默认文件创建独立的数据源第 1 版，绝不复制来源客户当前数据源。
12. 管理区启用可信网络限制后，非可信来源即使已登录也无法访问页面和 API；伪造 `X-Forwarded-For` 无效。
13. 密钥不通过列表或详情 API 返回明文，数据库泄露时密钥值仍为加密状态。
14. 备份恢复到另一台机器后，用户、客户、功能、数据源、配置、日志和定时任务完整，依赖环境可重建。
15. 浏览器登录使用随机不透明会话 Token；原始 Token 不写入 SQLite、日志或前端存储，只通过受保护 Cookie 传输。
16. 用户停用、密码重置、角色变化和管理员强制下线能够立即终止已有会话；移除客户关联后旧会话也不能继续访问该客户。
17. 所有修改 API 必须通过 CSRF 校验；伪造来源头、查询参数 Token 或过期会话均被拒绝。
18. 在有效期内刷新页面、关闭并重开浏览器、重启容器和更新镜像后登录仍然有效；备份恢复必须统一吊销旧会话。

## 25. 风险与客观限制

1. **SQLite 适合当前单机小规模场景，但不是无限并发队列。** 如果未来出现多主机 Runner 或持续高频日志，应重新评估数据库，而不是硬撑。
2. **强制停止不等于业务回滚。** 第三方接口已受理的操作无法由平台撤销。
3. **脚本日志质量由脚本负责。** 平台保证收集和保存，不保证业务覆盖率。
4. **可信网络必须由部署方给出事实依据。** 系统可以辅助识别当前地址，但不能猜出公司的真实网络边界。
5. **Python 依赖可以自动化，操作系统依赖不能无条件动态安装。** 后者必须重建镜像。
6. **单容器减少运维成本，也限制水平扩展。** 这是本项目现阶段的主动取舍，不是通用架构结论。
7. **公网安全仍需要 HTTPS 和基础网络防护。** 应用自身的认证、授权和网络门不能替代 TLS、防火墙和及时更新宿主机。

## 26. 技术依据

- Python 子进程和进程组是可控启动、等待和终止外部程序的标准基础：[Python `subprocess` 文档](https://docs.python.org/3/library/subprocess.html)
- Docker 容器停止先发送终止信号并在超时后强制结束：[Docker `container stop` 文档](https://docs.docker.com/reference/cli/docker/container/stop/)
- 单容器确实可以通过包装脚本或进程管理器运行多个内部进程，但应明确管理生命周期：[Docker 多服务容器文档](https://docs.docker.com/engine/containers/multi-service_container/)
- 反向代理头只有在代理数量和信任边界配置正确时才可采用：[Flask ProxyFix 文档](https://flask.palletsprojects.com/en/stable/deploying/proxy_fix/)
- SQLite WAL 适合本机多读少量写并发，但仍只有一个写者，并且不适合网络文件系统：[SQLite WAL 文档](https://sqlite.org/wal.html)
- 在线备份应使用 SQLite Backup API 获得一致快照：[SQLite Online Backup API](https://www.sqlite.org/backup.html)
- Python 虚拟环境被设计为可丢弃和重建，而不是跨位置搬运：[Python `venv` 文档](https://docs.python.org/3/library/venv.html)
- 离线 wheel 下载和本地安装是 pip 支持的标准流程：[pip 用户指南](https://pip.pypa.io/en/stable/user_guide/)
- 会话、认证、密码、CSRF 和上传安全边界参考：[OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)、[OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)、[OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)、[OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)、[OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)
