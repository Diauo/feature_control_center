# 1.1.0 通用执行结果报表设计

## 1. 目标与边界

运行日志适合排查过程，但业务人员不能依靠阅读自由文本或 JSON 枚举来统计一次同步的总数、成功数和失败数。1.1.0 增加一条独立的结构化结果通道，使功能脚本可以把已经判定的业务结论交给平台保存、中文展示和导出。

这项能力不改变平台的业务边界：

- 平台不定义商品、店铺、订单或库存模型；
- 平台不解析 XLSX，也不从日志内容推断结果；
- 成功、失败、无数据、跳过和未完成由脚本判定；
- 平台不提供失败项重跑、自动补偿或业务网络重试；
- 报表字段由每个功能版本声明，不要求不同功能共享业务主键；
- `request_id` 仍是一次运行的系统唯一标识。

## 2. 契约

功能包在 `__meta__.report` 中声明标题、业务对象名称和列：

```python
"report": {
    "title": "库存同步结果",
    "item_label": "商品",
    "columns": [
        {"key": "sku", "label": "商品编码", "type": "string"},
        {"key": "storeCode", "label": "店铺编码", "type": "string"},
        {"key": "quantity", "label": "库存", "type": "integer"},
    ],
}
```

元数据在上传时静态读取并规范化。列数限制为 1—30，支持字符串、整数、有限数字和布尔值；键名与标签限长，保留名称和疑似密钥字段会被拒绝。报表声明随不可变功能版本保存，任务运行时冻结到一次性输入快照。

SDK 提供 `ctx.report.start()` 和五种逐条提交方法。2.1.2 起单次运行默认最多 60000 条明细，管理员可在系统设置中于 1—1000000 范围内调整。任务启动时把当次上限写入隔离输入快照，SDK 与 Runner 二次校验使用相同值；运行中修改设置只影响后续任务。单条事件最多 12 KiB，字符串字段最多 2000 字符，原因最多 1000 字符；脚本直接伪造输出不能绕过服务端限制。

## 3. 传输与持久化

报表沿用 Runner 已有的随机事件令牌通道，但使用独立事件种类：

```text
report.start -> report.item * N -> report.complete
```

`report.item` 与普通日志可以在 stdout 中交错。Runner 排空输出后先保存所有报表指令和日志，再封存任务与报表，因此正常退出时不会出现页面已经显示终态、最后一批结果还未写入的竞态。

数据库使用两张表：

- `run_report`：一对一绑定运行，保存冻结列声明、预计总数、已提交总数、五类汇总计数、校验错误数和完整性；
- `run_report_item`：保存单次运行内严格递增的序号、平台状态、可读原因、可选原因代码、业务字段 JSON 和毫秒时间戳。

汇总计数与明细写在同一 SQLite 短事务内。运行列表批量读取当前页报表，不产生逐行查询。60000 条默认上限可以覆盖五万条业务数据；更高上限会增加 SQLite 文件、备份和 Excel 导出的时间及内存占用，调整前应按实际字段大小验证。

## 4. 完整性规则

报表只有同时满足以下条件才标为 `COMPLETE`：

1. 功能进程以成功状态结束；
2. SDK 已提交完成标记；
3. 服务端没有拒绝报表指令；
4. 如果声明了预计总数，已提交明细数与其一致。

其他情况统一标为 `INCOMPLETE`。预计但未提交的数量计入页面“未完成”，但平台不会凭空创建带商品信息的假明细。已经由脚本明确提交的 `UNFINISHED` 与未提交差额分别保存、汇总时相加。任务的 `SUCCEEDED` 只表示进程按协议正常退出；报表 `COMPLETE` 才表示脚本提交的结果集合通过结构完整性检查，两者不能互相替代。

旧功能包没有报表声明时不创建报表记录，也不影响原有运行和日志。平台不会尝试转换历史 JSON 日志，因为不同功能的枚举和值含义无法可靠推断。

## 5. 页面与导出

- 工作台顶部“已登记功能”卡片提供通用上传入口，不依赖具体业务功能；
- 运行记录主表显示报表总数、成功数、失败数和其他必要计数；
- 运行详情分为“最终报表”和“实时日志”，终态且有报表时默认打开报表；
- 明细列来自功能版本声明，五种状态始终显示为中文；
- 日志 JSON 上下文折叠为“技术字段”，避免业务人员被内部枚举干扰；
- 终态报表可下载 XLSX，包含“执行汇总”和“结果明细”；
- 导出文本对 `= + - @` 前缀做公式注入防护，下载接口逐任务校验客户权限并写安全审计。

## 6. 保留、备份与升级

报表明细与任务日志共用 `logs.retention_days`。清理到期日志时，在同一批次删除 `run_event` 和 `run_report_item`，并分别记录清理时间；`run` 和 `run_report` 汇总行继续保留。这样不会额外增加甲方的设置负担，也不会因保留全部逐条数据让 SQLite 无限制增长。

数据库迁移 `0010_report_limit` 把原有 5000 条数据库检查约束升级为与系统设置绝对范围一致的 1000000 条上限。升级前仍由 Launcher 使用 SQLite Online Backup API 生成一致性备份；迁移不改写既有报表数据。若已经存在超过 5000 条的报表，数据库会拒绝危险降级，避免为满足旧约束而截断数据。备份、恢复和迁移继续以整个 `data/` 为边界，不增加外部服务或宿主机环境变量。

## 7. 验证重点

- 正常完成：汇总与明细一致，报表为完整，Excel 中文状态正确；
- 主动停止：保留已提交明细，差额计入未完成，页面不冻结；
- 异常与中断：报表不能误标完整；
- 非法字段、类型、数量和过大事件：Runner 拒绝并留下平台警告；
- 客户越权：报表摘要、明细和下载均拒绝；
- 清理：删除明细后汇总仍可查看，明细接口和 Excel 返回已清理状态；
- 兼容：未声明报表的旧功能仍按原流程运行并下载日志。
