# 2.3.0 功能与用户删除

## 1. 背景

平台最初刻意不提供删除能力（保留审计与业务追溯）。甲方需要删除功能，因此本版实现「审计安全的删除」：功能删除后历史运行仍可查询，重新上传可恢复原登记；用户删除保留审计快照。

## 2. 功能删除（软删除登记）

数据模型：`customer_feature` 增加 `is_deleted`、`deleted_at`、`deleted_by`（迁移 0012）。

为什么必须是软删除：

- `run` 对 `customer_feature`、`feature_version`、`data_source_revision` 的外键是 **RESTRICT**，历史运行必须保持可关联；
- `(customer_id, feature_definition_id)` 唯一约束决定：重新上传必然复用同一注册行，「继承历史日志」由此天然成立。

删除行为：

- 登记行标记删除、`is_enabled` 置否、当前数据源指针置空；
- 配置值整表删除（含密钥密文）；定时任务删除；
- 数据源修订：被历史运行引用的清空内容并保留行（外键 RESTRICT），未被引用的整行删除；
- **保留**：登记行、功能版本记录与包体（共享资源，可能被其他客户引用）、全部运行/事件/报表。

访问控制：`feature_admin` 菜单 + 客户范围 + 最近认证；存在活动任务（QUEUED/STARTING/RUNNING/STOPPING）时拒绝。所有功能操作入口（列表、运行创建、配置、数据源、复制源、调度）对已删除登记统一返回 `FEATURE_DELETED`。

## 3. 恢复（重新上传 / 复制）

- 上传同名定义：该客户存在已删除登记时恢复——包内容已登记过则复用既有版本，否则绑定新版本；
- 复制到该客户：存在已删除登记时恢复而不是跳过；
- 恢复时重建配置默认值与默认数据源（修订号接续递增），状态按版本与数据源重新推导；
- 历史运行因登记行 id 不变而自动延续。

## 4. 用户删除

- 仅业务员账号可删除；系统管理员与当前登录账号不可删除；需最近认证；
- 显式清理登录会话；客户关联与菜单授权随 ORM 级联清理；
- 审计保留：`audit_log` 保存操作者与目标快照（用户名/显示名/角色），用户行删除不影响历史查询。

## 5. 前端

- 功能管理：卡片「删除功能」按钮 + 确认弹窗；上传结果为恢复时提示「功能已恢复」；
- 用户管理：业务员行「删除」按钮 + 确认弹窗；
- 删除动作统一走敏感操作重认证流程；删除与恢复均写入安全审计。
