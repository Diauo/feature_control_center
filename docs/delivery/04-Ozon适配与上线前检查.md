# OZON 适配与上线前检查

## 1. 输入基线

本次适配基于甲方提供的 `ozon_Inventory.zip`，原始文件 SHA-256：

```text
DFF7ED7776BB9C76B1AB260AD0F489DB1E8E613B8ACCD41C1633865B6318DDDF
```

源代码位于 `examples/feature-packages/ozon_inventory/`，可上传包位于 `feature-packages/`。平台团队没有改写库存计算、店铺筛选、接口地址默认值和更新判断。

## 2. 已完成的平台适配

1. 删除元数据中的固定客户名，客户归属改由后台注册操作决定；
2. 把旧式二元组配置改成带类型、标签和说明的正式配置定义；
3. 将 ME3/OZON 凭据声明为 `secret`，包内不保存默认密钥；
4. 明确声明 `dataSource.xlsx` 为必填数据源；
5. 脚本优先使用 `ctx.get_data_source_path()` 取得本次客户快照；
6. 增加 `pandas`、`openpyxl` 和 `requests` 依赖清单；
7. 平台上下文保留 `ctx.error()` 兼容入口，使原脚本错误日志进入实时日志；
8. 保留原来的 `run(configs, ctx)` 入口和三元组执行结果。

这些改动解决“同一份代码复制给多个客户，但每个客户使用自己的数据源和配置”的平台接入问题。

## 3. 数据源要求

文件名在功能包中声明为 `dataSource.xlsx`。平台允许用户下载当前文件，或上传新的 `.xlsx` 替换。表格至少应有：

| 字段 | 原脚本用途 |
| --- | --- |
| `sku` | ME3 商品/条码识别值 |
| `store_code` | 一个或多个 ME3 仓库代码，原脚本按英文逗号拆分 |

平台不校验 Excel 表头和内容。业务方应建立自己的模板版本、填写规范和复核责任人。

## 4. 必填配置

- `ME3_url`
- `ME3_app_key`
- `ME3_secret`
- `OZON_api_key`
- `OZON_client_id`
- `limit_Warehouse_id`

OZON 四个 API 地址带原脚本默认值。正式运行前仍需与当前 OZON Seller API 文档核对接口版本，不能因页面有默认值就视为长期有效。

## 5. 上线阻断项

以下内容属于原业务代码风险，平台没有越界代改。业务负责人处理并在测试店铺签字确认前，不得在生产店铺运行：

1. ME3 请求使用 `verify=False`，关闭了 TLS 证书校验，存在中间人篡改库存响应的风险；
2. 所有外部 HTTP 请求都没有显式连接/读取超时，网络挂起时只能依赖 Runner 最终强制停止；
3. 网络异常只转换为返回消息，没有按甲方约定实现有限自动重试；
4. 更新请求中的 `stock` 使用循环最后一次取得的 `ME3_inventory`，而日志和比较使用 `total_ME3_inventory`；多仓库时两者可能不一致；
5. 最外层异常日志引用 `sku`，如果异常发生在 `sku` 赋值前，错误处理本身可能再次异常；
6. `limit_Warehouse_id` 当前按字符串配置，需核对 OZON 返回的 `warehouse_id` 实际类型；
7. 个别“无有效数据/无需更新”路径写为错误级日志，业务语义可能更适合提示或警告；
8. 原脚本结束时即使中途接口失败，也可能返回成功三元组，需要业务方定义整批成功标准。

这些问题会影响库存正确性和最终结论，不能由通用调度平台猜测处理。

## 6. 联调顺序

1. 新建专用测试客户；
2. 上传 online 包，确认依赖准备成功；完全离线且为 Linux x86_64 时才使用 offline 包；
3. 填写测试店铺密钥，不使用生产凭据；
4. 上传只含 1—3 个测试 SKU 的数据源；
5. 在 OZON/ME3 侧记录运行前库存；
6. 手工运行并实时观察每个 SKU 日志；
7. 核对运行后库存、最终日志和请求 ID；
8. 验证停止、超时和网络断开时的业务结果；
9. 业务开发修复阻断项并上传新版本；
10. 测试负责人、库存业务负责人共同确认后，再复制功能到生产客户并替换各自数据源。

平台交付验收通过，只说明调度、数据源、日志和停止链路正常，不代表 OZON 业务脚本已通过生产验收。
