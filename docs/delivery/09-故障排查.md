# 故障排查

## 1. 固定排查顺序

先保存现状，再做变更：

```bash
date
df -h
free -h
docker version
./manage.sh status
./manage.sh logs 300
```

不要一上来删除容器、`data/`、依赖缓存或更新目录。很多问题在删除现场后无法追溯。

## 2. 网站打不开

1. `./manage.sh status` 是否显示 healthy；
2. `curl --fail http://127.0.0.1:8080/api/health/live` 是否成功；
3. 本机成功、外部失败：检查反向代理、防火墙、域名和证书；
4. 容器不健康：执行 `./manage.sh logs 300`；
5. 端口冲突：`ss -lntp | grep 8080`；
6. 磁盘满：先扩容或按正式保留策略处理，不直接删 SQLite/WAL。

## 3. 忘记首次验证码

```bash
./manage.sh setup-code
```

如果提示不存在，系统可能已初始化。不要尝试删除数据库重新初始化，应由现有管理员重置账号或走正式恢复流程。

## 4. 配置管理进不去

如果普通页面可用、配置区提示网络不允许，先检查安全审计里的客户端 IP 与可信代理设置。确认是误锁后，在服务器执行：

```bash
./manage.sh admin-access-reset
```

随后登录重新配置。该命令不解决账号密码错误。

## 5. 功能包上传失败

按页面错误处理：

- 根目录缺 `__init__.py`：去掉外层文件夹再打包；
- 元数据无效：保证 `__meta__` 是唯一字面量；
- 格式被禁用：管理员在系统设置勾选对应格式；
- RAR 解码组件不可用：检查是否使用正式交付镜像以及 `7zz i`；
- 路径/链接/压缩比异常：重新用普通文件打包，不降低安全限制；
- 大小超限：去掉无用文件或经评审调整系统上限。

## 6. 依赖准备失败

1. 查看功能版本的准备错误；
2. 核对 requirement 是否精确、是否有 Python 3.14 和目标架构 wheel；
3. 在线包检查服务器到软件源的 DNS、TLS 和代理；
4. 离线包检查 `wheels/` 是否包含完整间接依赖；
5. 修正后使用准备重试，或上传新版本；
6. 不进入容器手工 `pip install`，手工改动无法迁移和审计。

如果准备状态为可用、运行时仍出现虚拟环境或 `bin/python` 的 `Permission denied`，不要把目录直接 `chown` 给 `fcc-script`。先保存 Launcher 和 Runner 日志，再重启正式容器，让 Launcher 按 `root:fcc-script` 只读模型修复历史缓存。仍失败时检查是否存在异常符号链接或非正式镜像。

如果业务接口提示签名时间超出允许范围，先确认后台“系统时区”，再在测试功能中记录 `datetime.now().astimezone()`。正式镜像会把后台时区注入功能进程；不要在功能包和 Compose 中分别写死两个时区。

## 7. 任务一直运行

1. 从运行详情看最后一条业务日志；
2. 点击停止并等待宽限期；
3. 检查脚本是否在循环调用 `ctx.raise_if_cancelled()`；
4. 检查 HTTP 请求是否缺超时；
5. 检查系统设置和客户功能的最长运行时间；
6. Runner 最终会结束独立进程；不要重启整台服务器代替定位。

如果脚本创建了子进程，已违反功能包契约，必须改脚本。

## 8. 实时日志断开

页面断开不代表任务停止。刷新运行详情会从数据库序列续读。若没有新日志：

- 查看任务状态是否仍为运行中；
- 查看程序日志中的 Web/Runner 错误；
- 检查反向代理是否缓冲或过早关闭事件流；
- 检查脚本输出是否 flush；使用 `ctx.log` 会自动 flush。

## 9. 最终报表没有生成或显示“未完整”

- 页面提示“没有提交结构化报表”：该功能包没有声明 `__meta__.report`，或脚本没有调用 `ctx.report.start()`；旧功能的实时日志仍可使用；
- 预计总数大于已形成明细：检查循环中的异常分支是否漏掉 `success/failed/no_data/skipped/unfinished`；
- 校验错误数不为零：从实时日志查找“结构化报表有指令被拒绝”，按提示核对字段名、类型、长度和数量；
- 提示超过单次报表明细上限：在“系统设置 → 系统参数 → Runner 与任务日志”核对上限。默认值为 60000，修改后需要重新发起任务，正在运行的任务继续使用启动时的设置快照；
- 任务已停止、超时、失败或中断：报表显示“未完整”是正确结果，不要手工改成成功；
- 明细已清理：汇总仍保留，但明细和 Excel 不能恢复，只能从清理前的整包备份取回；
- 不要通过修改前端枚举或解析某个项目的日志 JSON 修正报表，应在对应功能脚本的业务判定位置提交正确结果。

## 10. 定时任务没触发

1. Scheduler 状态和心跳；
2. 定时任务是否启用；
3. 系统时区和下一次触发时间；
4. 客户功能是否启用且版本可用；
5. 配置和必需数据源是否完整；
6. 并发策略是否跳过本次触发；
7. 安全审计和程序日志中的调度记录。

## 11. 更新失败

不要手工改 `data/releases/current.json`。系统会自动回退并保留错误。记录更新 ID、阶段、错误、包 SHA-256 和 Launcher 日志。满足页面条件时使用原包重试；否则由发布人员重新制作更高版本更新包。

## 12. 备份恢复失败

- SHA-256 失败：重新传输，不绕过；
- 缺 `fcc.db`：不是本系统完整备份；
- 预检失败：保留候选目录和日志；
- 启动失败：脚本自动恢复原目录；
- 自动回退也失败：停止操作，保留 `data*` 所有目录并联系技术支持。

求助时提供：系统版本、故障时间、请求 ID/更新 ID、`./manage.sh status`、相关程序日志和已做操作。不要发送明文密钥或完整生产数据源。
