# 0.0.9 实现说明：运行日志保留与自动清理

版本：`0.0.9`  
阶段基线：[`phase-c.md`](./phase-c.md)

## 1. 策略

系统设置 `logs.retention_days` 默认值为 180，允许范围为 0 到 3650。0 表示明确关闭自动清理。保留期按照终态任务的 `finished_at` 计算；达到边界的任务可以被清理。

自动清理只选择：

- 状态为 `SUCCEEDED/FAILED/STOPPED/TIMED_OUT/INTERRUPTED`；
- `finished_at` 已确定；
- 尚未记录 `logs_purged_at`；
- `finished_at <= 当前时间 - 保留天数`。

活动任务永远不会被日志保留任务选中。

## 2. 为什么保留任务摘要

清理器删除 `run_event`，但保留 `run`。因此系统仍能回答某个 request ID 是否存在、属于哪个客户和功能、使用哪个版本及数据源、何时运行、最终是什么状态。`last_event_sequence` 和 `final_event_sequence` 作为历史封存元数据保留，不会在日志删除后伪装成从未产生日志。

`1.1.0` 起，`run_report_item` 与运行日志使用同一保留期限并在同一清理批次删除，避免新增一套甲方需要维护的设置。`run_report` 的汇总计数和完整性状态继续保留；明细清理后页面明确显示清理时间，明细接口和 Excel 下载不再返回内容。

`run.logs_purged_at` 是可观察的清理事实。列表和详情接口都会返回 `logsPurgedAt`；前端显示“日志已清理”，下载按钮停用。直接访问 `.log` 或 `.jsonl` 下载接口返回 HTTP 410 和 `RUN_LOGS_PURGED`，而不是返回一个容易被误认为真实最终日志的空文件。

## 3. 调度和 SQLite 边界

清理由已经存在的单实例 Runner 执行，不新增定时服务、系统 cron 或容器。Runner 启动后的首轮会检查，正常情况下每小时再检查一次。每个事务最多处理 200 个任务；仍有积压时短暂让出执行机会后继续下一批，避免一次大删除长期占有 SQLite 写锁。

清理异常不会终止脚本监督。Runner 会记录自身错误并在 60 秒后重试，现有功能进程仍可继续被停止和回收。

SQLite 删除行后释放的页会被后续数据复用，但物理数据库文件不保证立即收缩。运行期间不自动执行 `VACUUM`，因为全库重写会增加锁等待和临时空间需求。需要压缩文件时，应先停止容器、备份整个数据目录，再由维护人员离线执行。

## 4. 数据和接口变化

- Alembic `0004_log_retention` 为 `run` 增加 `logs_purged_at`；
- 索引 `ix_run_log_retention(logs_purged_at, finished_at)` 支撑到期扫描；
- `GET /api/runs/{request_id}` 增加 `logsPurgedAt`；
- 事件分页增加 `logsPurgedAt`，已清理任务返回空事件集和原终态；
- SSE 遇到已清理任务会发送最终 `run` 事件后关闭，不会因历史序号仍存在而空转；
- 日志下载在已清理后返回 410。

## 5. 设置生效

设置保存在 SQLite，通过后台“系统设置”修改并受管理员权限、管理区网络门、CSRF 和近期身份验证保护。修改为更短保留期后，不会在保存请求内执行大删除；Runner 下一次保留检查时生效。这样后台 HTTP 请求不会承担清理耗时。
