# 阶段 D 实现说明：定时、复制和后台

版本：`0.0.10`  
架构基线：[`docs/architecture/0.0.5-system-design.md`](../architecture/0.0.5-system-design.md)

## 1. 本阶段闭环

阶段 D 完成四条平台能力，同时继续守住“平台只运行功能，不解释商品业务”的边界：

1. 独立 Scheduler 根据客户定时任务创建持久运行请求；
2. 管理员可把一个已有客户功能快捷复制给多个目标客户；
3. 运行记录支持按平台事实组合筛选；
4. 用户、客户、关联关系和系统设置页面补齐到日常可操作状态。

没有增加失败商品、商品主键、业务补偿或失败项重跑。定时触发只是另一种 `Run` 创建来源，脚本读取文件、同步远端数据和判断业务成败仍由甲方脚本负责。

## 2. Scheduler 的职责边界

容器现在包含 Launcher、Web、Runner 和 Scheduler 四个长期进程。Scheduler 使用 `fcc` 低权限账户运行，只访问平台数据，不需要 Runner 的 root 权限。它只执行三件事：

1. 读取到期的 `scheduled_task`；
2. 调用与手工运行共用的 `RunService` 固化版本、配置和数据源快照；
3. 创建 `trigger_source=SCHEDULED` 的 `QUEUED` 记录。

Scheduler 不导入功能代码、不创建脚本子进程、不持有脚本 PID，也不收集日志。Runner 仍是唯一可以领取队列并改变运行中状态的进程。这样定时功能不会重新引入“脚本由某个临时 Web/定时线程拉起后停不下来”的根问题。

`launcher` 会同时监督 Web、Runner 和 Scheduler；任一关键进程退出都会让容器退出并交给 Docker 重启。正常停止时先停 Scheduler，避免关停窗口继续创建任务，再停 Runner 和 Web。

## 3. 定时表达式与时区

### 3.1 用户入口

前端提供四种模式：

- 每天：选择时间；
- 每周：选择星期和时间；
- 每月：选择日期和时间；
- 高级 Cron：填写标准 5 段表达式。

前三种最终也保存为 Cron，因此后端只有一套计算和校验规则。首版刻意不支持秒字段、自然语言计划或复杂工作流。

### 3.2 时区

系统设置 `system.timezone` 保存 IANA 时区，默认 `Asia/Hong_Kong`。每条定时任务同时保存计算时采用的时区，页面按该字段展示下次执行时间。管理员修改全局时区后，Scheduler 会从当前时间重新计算所有启用任务，并更新任务时区；不会用新时区回放旧时点。Runner 启动每个功能进程时把当前设置作为 `TZ` 注入最小环境，功能代码使用 `datetime.now()` 时与后台时区保持一致。

项目固定 `croniter==6.2.4` 和 `tzdata==2026.3`。Python `tzdata` 保障 `ZoneInfo` 计算，正式镜像同时安装系统 `tzdata`，保证子进程的 POSIX `TZ` 环境变量也能解析完整 IANA 时区。容器和平台程序日志保持 UTC 基线，业务功能进程按后台设置覆盖；Cron 计算继续使用带时区的 `datetime`，避免把夏令时区域永久当作固定 UTC 偏移。

### 3.3 无补跑策略

系统设置：

- `scheduler.poll_interval_seconds`：默认 5；
- `scheduler.heartbeat_seconds`：默认 5；
- `scheduler.stale_after_seconds`：默认 30，必须至少是心跳的 3 倍；
- `scheduler.misfire_grace_seconds`：默认 60。

若 `当前时间 - 计划时间` 超过错过容差，本次标记为 `MISSED`，`missed_count` 加一，然后直接从当前时间计算未来时点。系统恢复后不会集中补跑离线期间的同步任务。这样可以避免对外部平台产生未经确认的重复写入。

## 4. 防重复与单实例

`scheduler_heartbeat` 保存 Scheduler 实例令牌、PID 和心跳。第二个健康进程会拒绝获得调度权；失联实例可以被新进程接管。

单实例不是唯一防线。每次计划触发使用：

```text
trigger_key = schedule:<scheduled_task.id>:<planned_epoch>
```

`run.trigger_key` 有数据库唯一约束。即使 Scheduler 在“运行记录已提交、定时任务尚未推进”之间崩溃，重启后再次处理同一时点也只能读到已有运行，不会创建第二条。推进任务时还会比较数据库中的 `next_run_at` 是否仍是原计划时点，避免并发编辑覆盖用户的新设置。

同一客户功能已有活动运行时记录 `SKIPPED_ACTIVE`；队列满记录 `QUEUE_FULL`；客户、功能、版本、配置或数据源不可用时记录 `SKIPPED_UNAVAILABLE`。这些都是该计划时点的处理结果，不会由平台自动重试整个业务任务。

## 5. 快捷复制的隔离规则

快捷复制只允许管理员在管理区执行，需要 CSRF、可信网络策略和近期密码复验。一次最多选择 200 个目标客户，每个目标独立事务并返回逐客户结果：`COPIED`、`SKIPPED_EXISTS` 或 `FAILED`。

复制的数据：

- `feature_definition` 身份；
- 当前 `feature_version` 引用；
- 版本中的展示名称、说明和配置结构；
- 非密钥配置默认值；
- 功能版本 ZIP 内的默认数据源内容。

不复制的数据：

- 来源客户已经填写的普通配置和密钥；
- 来源客户当前数据源及其历史；
- 功能级最长运行时间覆盖；
- 定时任务；
- 运行记录和日志。

目标客户的代码仍指向同一个不可变版本，因此复制到很多客户不会重复存 ZIP 或安装依赖。若版本有默认数据源，系统为每个目标各自创建 `customer_feature_data_source_revision` 第 1 版。即使文件字节相同，修订 ID 和客户功能归属也不同。目标客户之后下载、替换、创建运行快照时只访问自己的记录。

目标客户已存在同一功能时返回 `SKIPPED_EXISTS`，不会暗中切换版本或覆盖目标客户数据。一个目标失败会回滚该目标事务，不影响已经成功或尚待处理的目标。

## 6. 运行记录查询

`GET /api/runs` 新增组合筛选：

- `customerFeatureId`；
- `status`；
- `triggerSource=MANUAL|SCHEDULED`；
- `queuedFrom`、`queuedTo`（Unix 秒）；
- `requestId`（1 到 32 位十六进制前缀，也可完整匹配）；
- `limit`（最多 200）。

后端始终先约束用户可访问的 `customerId`，前端参数不能绕过客户权限。首版不增加日志全文检索，不建立 FTS 索引，也不把日志内容解释成商品查询。这符合甲方“不需要查询能力，只需记录同步过程”的边界，并保持 SQLite 简单可迁移。

## 7. 后台与设置

已有用户管理、客户管理和用户—客户多对多关系页面保持不变并纳入阶段 D 验收。系统设置页面新增：

- 系统名称和 IANA 时区；
- 会话闲置期限、绝对期限、近期复验窗口、每用户会话数；
- Scheduler 轮询、心跳、失联和错过容差。

这些日常参数继续保存在 SQLite，不要求部署人员编辑环境变量。系统设置仍只对管理员开放，并经过管理区网络门、CSRF 和近期身份验证。

业务操作员可以在自己关联的客户内查看、新建、编辑、停用和删除定时任务；不能访问管理员配置、功能包、用户或客户后台。客户功能外键和每次服务端权限校验共同保证不能通过修改 URL 跨客户操作。

## 8. 数据库与迁移

Alembic `0005_phase_d` 新增：

- `scheduled_task`：客户、客户功能、Cron、时区、启用状态、下次时点、最近结果和累计错过次数；
- `scheduler_heartbeat`：单 Scheduler 所有权和健康状态；
- 到期扫描、客户列表和功能关联索引。

`scheduled_task` 随客户或客户功能删除而删除。运行记录只保存触发后的事实，不反向依赖定时任务，因此删除一个计划不会破坏既有运行日志。

## 9. 新增接口

```text
GET    /api/schedules?customerId={id}
POST   /api/schedules
PUT    /api/schedules/{id}
DELETE /api/schedules/{id}
POST   /api/admin/customer-features/{id}/copy
```

`GET /api/runs` 继续使用原路径，只增加可选筛选参数。接口未返回配置快照、密钥或客户文件内容。

## 10. 客观限制

1. 每月 29、30 或 31 日的计划在没有该日期的月份自然跳过；这是 Cron 语义，不自动改成月末。
2. Scheduler 是单机单实例方案，符合当前 SQLite、低业务量和易迁移约束；不是分布式调度器。
3. 防重复保证同一计划时点只创建一个平台运行，不保证甲方脚本对第三方系统的业务写入幂等。
4. 调度跳过和错过只保存最近结果与累计错过次数，不增加一套无限增长的调度事件表；真正创建的任务仍由 `run` 和 `run_event` 完整留痕。
5. 删除定时任务是明确操作；既有运行记录保留，但不提供定时任务回收站。
6. 功能复制以版本默认文件初始化，不能用于跨客户搬运当前业务文件。如果以后确有该需求，应设计为独立、有强提示和审计的数据导入，而不是改变普通复制语义。

## 11. 验证范围

本阶段最终验证覆盖：快捷复制的代码共享/配置隔离/密钥隔离/默认文件独立修订，Scheduler 入队、防重复、错过不补跑，操作员客户权限，运行组合筛选，既有 Runner 与安全回归，前端单元测试、类型检查和生产构建。

最终结果：

- 后端：28 项测试全部通过；分支覆盖统计总覆盖率 71%；
- 前端：5 项 Vitest 测试全部通过；
- TypeScript：`vue-tsc` 和 Node 配置 `tsc` 通过；
- 前端：Vite 生产构建通过，产物已同步到 Flask 静态目录；
- 原 `features/` 目录未修改；
- 当前开发机未提供 Docker CLI，镜像构建、Linux UID 降权和真实容器信号链仍需在阶段 E 的交付验收机验证。
