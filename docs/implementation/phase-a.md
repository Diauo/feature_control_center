# 阶段 A 实现说明：骨架与安全基础

版本：`0.0.6`  
架构基线：[`docs/architecture/0.0.5-system-design.md`](../architecture/0.0.5-system-design.md)

## 1. 阶段目标与结论

阶段 A 只解决后续功能运行平台无法绕开的四件事：

1. 建立可继续扩展而不互相污染的代码分层；
2. 建立可迁移、可搬运、启动失败时能够保护数据的 SQLite 实例；
3. 建立不会把长期 Token 暴露给 JavaScript 的登录和服务端会话；
4. 建立用户—客户多对多权限边界、管理界面与安全审计。

这个顺序比先接业务脚本慢一步，但能避免后续为每个功能重复补登录、客户过滤、审计和迁移逻辑。

## 2. 代码边界

### 2.1 后端

| 层 | 当前职责 | 禁止事项 |
| --- | --- | --- |
| `domain` | 用户名、角色、客户名称、密码输入规则等纯规则 | 不依赖 Flask、SQLAlchemy 或文件系统 |
| `application` | 初始化、登录、会话、用户、客户、审计用例 | 不解析 HTTP Cookie，不返回 Flask Response |
| `infrastructure` | SQLAlchemy 模型、SQLite 连接、Alembic、实例文件 | 不决定页面跳转或业务权限 |
| `security` | Argon2id、HMAC、随机 Token、CSRF 原语 | 不直接访问请求对象和数据库 |
| `web` | 路由、Cookie、CSRF/Origin 装饰器、错误映射、静态页面 | 不内嵌 SQL 和密码学实现 |

`runner`、`scheduler` 和 `sdk` 目前只有清晰的包边界，没有伪造尚未实现的运行能力。阶段 C 仍必须让 Runner 与 Web 分离，Flask 请求处理线程不能直接持有业务脚本进程。

### 2.2 前端

- `stores/session.ts` 只保存当前用户、可访问客户和非敏感的当前客户选择；
- `lib/api.ts` 统一携带 Cookie、维护 CSRF、把接口错误映射成 `ApiError`；
- 路由守卫处理未初始化、未登录、首次强制改密和管理员页面；
- 页面组件不读取 Cookie，也无法读取 `HttpOnly` 会话 Token。

## 3. SQLite 策略

- 使用 Alembic 维护结构版本；应用启动时先迁移再提供服务；
- 每个连接执行 `foreign_keys=ON`、`busy_timeout=5000`、`synchronous=FULL`；
- 数据库启用 WAL，读请求不会因为短写事务完全串行化；
- SQLAlchemy Session 使用短事务，路由层不长期持有数据库连接；
- 镜像编译 SQLite 3.53.4，并在构建时断言版本不低于架构要求的 3.51.3；
- `fcc.db` 和 `instance.key` 组成同一个逻辑实例，缺失或指纹不匹配时拒绝启动。

SQLite 适合当前体量，但“WAL”不等于可以无限并发写。后续实时日志不能每行单独提交，阶段 C 需要按批次写入并让 Web、Runner、Scheduler 保持短事务。

## 4. 首次初始化

首次启动流程：

1. 创建 `data`、`runtime-cache` 和 `tmp`；
2. 以安全随机数生成 `instance.key`，文件权限尽可能限制为当前账户；
3. 执行数据库迁移并写入有边界的默认系统设置；
4. 生成一次性初始化码，只把摘要写入数据库；
5. 将明文码写入宿主机可见的 `first-run.txt`；
6. 初始化请求以条件更新原子占用该码，防止两个请求同时成为首个管理员；
7. 创建管理员、首个客户、关联关系、会话和审计记录；
8. 成功提交后删除 `first-run.txt`。

错误的初始化码也会写审计。初始化码不会硬编码进镜像、环境变量或源代码。

## 5. 登录与持久会话

### 5.1 会话模型

- 登录 Token：32 字节安全随机数，经 URL-safe Base64 编码；
- 浏览器：只在 `HttpOnly`、`SameSite=Lax` Cookie 中持有原始 Token；
- 数据库：只保存用实例派生密钥计算的 HMAC-SHA-256 摘要；
- HTTP 局域网模式使用 `fcc_session`；可信 HTTPS 请求使用 `__Host-fcc_session`；
- HTTPS Cookie 具备 `Secure`、`HttpOnly`、`Path=/`，没有 Domain；
- 默认闲置 8 小时、绝对 24 小时、最多 5 个并行会话；
- 每 5 分钟最多更新一次 `last_seen_at`，避免每个页面请求都产生 SQLite 写入；
- 密码、角色、启用状态变化通过 `security_version` 和会话吊销立即生效。

选择服务端会话而不是长期 JWT，是因为这里需要可靠退出、管理员强制下线、即时权限变更和容器重启后保留登录。服务端记录提供这些能力，SQLite 的额外负担在当前规模内很小。

### 5.2 密码

- Argon2id：内存 64 MiB、时间成本 3、并行度 1；
- 最少 12 字符，最多 256 字符且 UTF-8 不超过 1024 字节；
- 用户由管理员创建，临时密码只在创建或重置响应中显示一次；
- 临时密码首次登录后只能进入改密流程；
- 未知用户和停用用户都会执行虚拟密码校验，降低账号状态的时间侧信道差异。

### 5.3 防护

- 登录前使用短期签名 CSRF Token；
- 登录后使用与会话绑定的随机 CSRF Token；
- 修改请求同时检查 `X-CSRF-Token` 和存在时的 `Origin`；
- 账号和来源 IP 双维度登录限速，第 5 次失败后指数延长等待，最长 15 分钟；
- 用户管理敏感操作要求最近 10 分钟内重新验证密码；
- 统一返回不区分“账号不存在、已停用、密码错误”的登录错误；
- JSON 响应 `Cache-Control: no-store`；全局设置 CSP、禁止 iframe、MIME 嗅探、来源泄露和不需要的浏览器权限。

## 6. 反向代理与客户端 IP

系统不会把 RFC1918 私网地址写死为“公司内网”，也不会无条件信任 `X-Forwarded-For`：

1. 默认使用 TCP 直接对端地址；
2. 只有直接对端落入 `security.trusted_proxy_cidrs` 时才解析转发链；
3. 从最右侧开始剥离可信代理，保留第一个不可信跳作为客户端；
4. 只有可信直接代理可以用 `X-Forwarded-Proto` 声明 HTTPS；
5. Origin 校验使用解析后的 HTTP/HTTPS 状态，避免 TLS 终止代理后误判。

可信代理、管理区网络门及防锁死交互属于阶段 B/D 的设置页面，本阶段完成的是可信解析基础，不提前开放不完整的网络门。

## 7. 用户和客户

- `user` 与 `customer` 通过 `user_customer` 多对多关联；
- 管理员可管理全部启用客户，操作员只返回已关联且启用的客户；
- 关联不存在或客户已停用时不能分配；
- 用户停用、角色变化立即撤销全部会话；
- 不能停用或降级当前管理员；系统始终至少保留一名启用管理员；
- 当前管理员不能从后台“重置自己的密码”，必须走带当前密码校验的个人改密流程；
- 客户停用不删除历史记录，为后续功能、配置、数据源、日志引用保留稳定 ID；
- 前端当前客户 ID 只是界面偏好，后续每个业务 API 仍必须在服务端重新验证归属。

## 8. 审计

阶段 A 记录：首次初始化、登录成功/失败/限速、登出、重新验证、个人改密、用户创建/修改/关联、密码重置、会话吊销、客户创建/修改。

审计只保存动作、结果、操作人、会话 ID、目标、解析后的来源 IP、User-Agent 摘要和经过挑选的结构化详情。以下内容禁止写入审计：密码、临时密码、会话原始 Token、CSRF Token、实例密钥和未来的配置明文。

## 9. 阶段边界

阶段 A **没有**启动任何 `features` 脚本，也没有实现“看起来能点但实际上不可靠”的运行按钮。下一阶段先落功能包、版本、客户配置和客户独立数据源，再由阶段 C 建立可终止的独立子进程与实时日志。

完整阶段顺序仍以 `0.0.5-system-design.md` 为准：

- B：功能、配置、数据源、依赖准备；
- C：Runner、停止机制、实时/最终日志；
- D：快捷复制、日志查询、完整后台页面；
- E：定时任务、备份恢复、兼容验证、正式离线交付闭环。
