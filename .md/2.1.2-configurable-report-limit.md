# 2.1.2 可配置结构化报表上限

日期：2026-09-15

## 变更原因

生产业务一次会处理约五万条数据，而 1.1.1 在脚本 SDK、Runner 校验和 SQLite 检查约束中都把结构化报表限制为 5000 条。只修改某一个常量无法解决问题：SDK 可能提前拒绝，Runner 仍可能拒绝伪造事件，数据库也无法保存超过旧约束的计数。

## 设计决定

- 新实例的单次报表明细默认上限调整为 60000；
- 后台“系统设置 → 系统参数 → Runner 与任务日志”允许在 1—1000000 范围内修改；
- Runner 在任务启动时读取设置，并把上限写入该任务的隔离输入快照；
- 功能进程 SDK 和 Runner 服务端二次校验使用同一个运行级快照；
- 修改设置只影响之后启动的任务，正在运行的任务不会中途改变接收标准；
- SQLite 检查约束使用 1000000 的绝对安全上限，日常可调值仍由系统设置控制。

选择运行级快照而不是每条明细读取系统设置，是为了避免五万条任务执行途中被管理员修改设置后，SDK 与服务端产生不一致，也避免为每条明细增加数据库查询。

## 数据迁移

新增迁移 `0010_report_limit`。SQLite 不能直接修改检查约束，且 `run_report_item` 通过级联外键引用 `run_report`。迁移先在数据库内暂存全部历史明细，移除明细表后重建报表约束，再按原主键恢复明细和索引，防止重建父表时误删历史结果。

降级到旧约束前会检查是否存在超过 5000 条的报表。若存在，迁移明确拒绝降级，不截断、不删除数据。

## 性能与边界

- 60000 是默认业务容量，不代表建议把所有自由文本都塞进报表；
- 单条明细的 12 KiB、字符串长度、字段数量和敏感字段限制保持不变；
- 更高上限会增加 SQLite 文件大小、备份耗时和 XLSX 生成内存，修改前应使用真实字段规模验证；
- 平台继续不判定商品成功或失败，不提供失败项重跑，业务脚本仍通过 `ctx.report` 提交结论。

## 版本与源代码基线

- 产品版本按新的 2.x 版本线调整为 `2.1.2`；
- Python 包、前端包、Docker 标签、发布记录、交付文档和测试断言同步更新；
- 项目目录原先不包含 Git 元数据，也没有可用的 GitHub 远程地址。完成验证后会先建立不含历史包袱的本地 `release/2.0` 基线提交；推送前必须绑定用户指定的 GitHub 仓库，不能把业务源代码发送到猜测的账号或仓库。
