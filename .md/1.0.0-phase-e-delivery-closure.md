# 1.0.0 阶段 E：交付闭环

## 变更目标

把阶段 A—D 的运行系统整理为可以交接、部署、维护、开发功能包和恢复数据的正式交付物。交付以真实项目结构和甲方低运维能力为前提，不要求日常编辑环境变量，不把客户运行数据混入程序包，也不把业务脚本职责推给平台。

## 版本决策

本次从 `0.1.2` 提升到 `1.0.0`。原因是交付物首次形成稳定的部署入口、运维命令、备份恢复约定、功能包开发契约和验收边界，已经不只是页面细节修订。数据库结构没有新增迁移，现有 `0008_scope_paging_update` 数据可直接启动。

## 实施内容

### 1. 一键部署和统一运维

- 新增根目录 `install.sh`：校验交付文件、识别 Linux 架构、优先载入离线镜像、无镜像时从源码构建、启动单容器并等待健康检查；
- 新增根目录 `manage.sh`：统一提供启动、停止、重启、状态、日志、首次初始化信息、备份、恢复、配置区误锁恢复和完整性校验；
- 脚本不清空已有 `data/`，不提供危险的一键删除；
- 新增 `deployment/build-offline-bundle.sh`，在 Linux Docker 构建机完成镜像构建、容器健康检查、镜像导出和 SHA-256 生成。

### 2. 备份、恢复和迁移

- 备份在容器停止后封装整个 `data/`，而不是只复制 SQLite；
- 每个备份生成独立 `.sha256`；
- 恢复拒绝越界路径、链接和特殊文件；
- 候选数据先运行应用预检和数据库迁移，再切换目录；
- 恢复后健康检查失败时自动换回原数据；
- 恢复前自动再做一份安全备份，原数据目录不会立即删除。

### 3. 功能包交付材料

- 新增无网络、无第三方依赖的交付验收功能，用来验证数据源、实时日志、停止和最终日志；
- 新增正式起步模板，展示类型化配置、密钥、数据源、结构化日志和合作停止；
- 基于甲方 `ozon_Inventory.zip` 生成实际适配源：声明数据源、把凭据标为密钥、补充 requirements，并通过上下文取得客户数据源快照；
- 为 Linux x86_64 / Python 3.14 下载 OZON 依赖闭包 wheel，交付生成器可输出离线功能包；
- 原 OZON 库存计算、接口调用和业务成功标准未越界修改，已在专门文档列出上线阻断项。

### 4. 旧功能兼容

`FeatureContext` 增加 `debug`、`info`、`warning`、`error` 快捷方法并转发到结构化日志。这样原项目中使用 `ctx.error(...)` 的错误分支不会因上下文缺方法而二次失败，同时保留现有 `ctx.log(...)` 和 `ctx.log.info(...)`。

### 5. 交付生成和校验

- 新增 `tools/build_delivery.py`，从白名单目录生成客户交付 ZIP；
- 排除 `data/`、虚拟环境、node_modules、构建缓存、运行静态副本和私钥命名文件；
- ZIP 中的 shell 脚本写入 Unix 可执行权限和 LF 换行；
- 生成 `DELIVERY-MANIFEST.json` 和覆盖全部交付文件的 `checksums.sha256`；
- 根据是否存在真实 Docker 镜像明确标记 `offline-image` 或 `source-build`，不制造空镜像；
- 新增 `tools/verify_delivery.py`，复核顶层结构、文件集合、SHA-256、版本一致性、脚本格式、运行数据排除和内嵌功能包入口。

### 6. 专业交付文档

`docs/delivery/` 包含交付包说明、Linux 部署、管理员手册、功能包开发规范、OZON 适配检查、备份恢复、公网安全、系统更新、验收、排障、兼容性、第三方许可证和发布检查记录。

## 关键设计理由

1. **不自动安装 Docker**：不同 Linux 发行版、公司代理和防火墙策略不同，安装脚本擅自改主机软件源比多一步前置检查更危险；系统自身仍保持一条命令完成安装。
2. **整包备份而非单 SQLite**：`instance.key`、数据源、功能包、运行环境和更新回退材料都与数据库共同构成可恢复状态。
3. **恢复先候选预检再切换**：直接覆盖现有 `data/` 会把一个可恢复问题变成停机事故。
4. **镜像缺失时明确标记**：当前工作站没有 Linux Docker Engine，不能把未经构建验证的文件包装成 Docker 镜像；交付工具保留源码构建路径和正式镜像封装入口。
5. **不修改 OZON 业务风险**：平台与业务边界已经约定，通用平台不能擅自决定库存汇总、失败结论和 API 重试语义，但必须把发现的问题作为上线门记录。

## 验证范围

所有实现完成后只执行一轮统一发布验证：后端测试、前端测试、前端生产构建、静态资源同步、功能包检查、交付 ZIP 生成与交付完整性复核。Linux Docker 镜像构建和目标机容器验收因当前工作站缺少 Docker，必须在 Linux 构建机关闭该发布门。

## 验证结果

- 后端：48 项 pytest 全部通过；
- 前端：5 项 Vitest 全部通过，Vue/TypeScript 类型检查和 Vite 生产构建通过；
- 交付封装：231 个文件校验通过，4 个内嵌功能包通过平台正式规则；
- OZON：online/offline 两个包均通过静态检查，offline 包包含 12 个 Linux amd64 / CPython 3.14 wheel；
- 已知非阻断项：主前端 chunk 为 534.66 kB（gzip 178.32 kB）；
- 未验证项：Linux Docker 镜像构建与目标服务器容器运行，原因是当前工作站没有 Linux Docker Engine。
