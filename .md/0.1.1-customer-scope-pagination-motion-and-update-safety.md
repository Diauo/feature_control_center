# 0.1.1：客户聚合、分页、统一动效与更新恢复加固

## 1. 目标

本次版本集中解决四类生产问题：

1. 顶部客户选择只能查看单个客户，跨客户业务人员需要频繁切换；
2. 审计、运行、用户等列表没有真正的服务端分页，数据增长后页面和接口都会变慢；
3. 页面、子功能和客户切换直接替换 DOM，侧栏折叠后还存在多个提示同时打开的竞态；
4. 0.1.0 的签名更新边界正确，但候选进程启动、数据库恢复权限和断电目录持久化仍不满足交付要求。

版本由 `0.1.0` 提升至 `0.1.1`。本次没有增加客户或用户删除：停用仍是保留历史关联的唯一常规操作。

## 2. 客户范围模型

前端不再用空字符串混合表达“未选择”和“全部客户”。会话状态明确区分：

```text
customer + customerId
all
```

“全部客户”只代表当前账号被授权的有效客户。管理员可以查看全部有效客户；业务用户只能查看 `user_customer` 关联的客户。后端在每个聚合请求重新计算范围，不接受前端上传的客户 ID 集合作为授权依据。

工作台通过 `/api/customer-features` 聚合查询。每条结果携带 `customerId` 和 `customerName`，全部客户模式中的卡片在标题上方显示客户标识。运行、配置、数据源下载和替换仍绑定具体的 `customer_feature.id`，因此不同客户即使共享同一功能代码版本，也不会共享配置或数据源。

运行记录和定时任务同步理解全部客户范围，并显示客户列。新建定时任务和上传功能版本仍要求选择具体客户；处于全部客户范围时按钮会停用并说明原因，不会暗中使用上一次客户。

## 3. 分页协议

普通列表统一接受 `page` 和 `pageSize`，其中页码从 1 开始，每页最多 100 条。响应为：

```json
{
  "items": [],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "total": 0,
    "totalPages": 1
  }
}
```

分页覆盖客户、用户、审计、运行记录、定时任务、功能定义、系统更新任务和版本更新记录。前端共用 `PaginationBar.vue`，提供 20、50、100 三种页容量。筛选或客户范围变化时返回第一页。

任务实时日志和平台程序日志不改成页码式查询：它们继续使用增量游标，因为日志查看的核心行为是持续追踪新事件，而不是翻阅静态页。

## 4. 选择器

`SearchCombobox.vue` 将关闭状态和搜索状态分离：

- 关闭时是单一按钮，只显示当前值和箭头；
- 展开后才在浮层内显示搜索输入；
- 顶部客户选择使用轻量 `toolbar` 外观；
- 系统时区使用 `form` 外观；
- 选中和键盘高亮使用中性灰，蓝色只保留给可访问性焦点；
- “全部客户”固定在客户选项顶部并与具体客户轻分隔。

这个结构消除了全局 `.field input` 与组件内部输入框叠加造成的双层边框。

## 5. 动效系统

动效职责保持分离：

- Morphicons 负责折叠箭头和侧栏控制图标的形态变化；
- motion-v 负责子功能选中背景的共享布局动画；
- Vue Transition 和 CSS 负责页面、子面板和客户数据快照的淡入淡出。

系统设置、安全审计和用户类型共用 `AnimatedTabs.vue`。激活背景平滑移动，内容面板使用约 200ms 的低位移淡入淡出。主路由只按 `route.path` 过渡，查询参数变化不会造成整页动画。

所有非必要动画都受 `prefers-reduced-motion` 约束。子功能按钮保留 tab 语义，并支持左右方向键、Home 和 End。

## 6. 工作台切换一致性

工作台不再在请求开始时清空卡片。切换范围时保留旧数据并降低透明度，同时禁止其业务操作；新请求完成后一次性提交功能列表和分页快照。

每次请求使用递增序号。快速从 A 切到 B 再切到 C 时，较早响应不能覆盖较新的范围。切换失败后旧数据只供查看，不允许从与顶部范围不一致的卡片启动任务或替换数据源。

## 7. 侧栏提示竞态

侧栏 Tooltip 从多个非受控实例改为单一互斥键控制：任意时刻最多允许一个提示打开。开始折叠、导航点击、鼠标离开和展开侧栏都会清空状态；折叠动画期间不接受打开请求。

动画解锁优先依据 `width` 的 `transitionend`，定时器只作为浏览器未派发事件时的兜底，因此以后调整动画时长不会重新产生提示状态错位。

## 8. 系统参数折叠

系统参数按既有业务边界拆成可同时展开的 `SettingsSection.vue`：

- 系统与登录状态；
- 管理区网络保护；
- 功能包与数据源边界；
- Python 依赖准备；
- Runner 与任务日志；
- 平台程序日志与更新包；
- Scheduler。

默认只展开第一组。折叠只改变可见性，不销毁输入状态；关闭的内容使用 `inert` 移出键盘焦点顺序。展开高度使用网格行过渡，图标使用 Morphicons。全局保存按钮和现有后端设置协议不变。

## 9. 更新系统加固

### 9.1 候选进程事务

Web、Runner、Scheduler 顺序启动时，每个成功进程立即加入清理集合。任一后续进程启动失败，Launcher 会逆序终止已启动进程并等待退出，之后才允许恢复数据库或启动旧版本。

### 9.2 心跳绑定

候选就绪检查不再只比较时间戳和状态，而是同时验证候选 Runner/Scheduler 的 PID、启动时间、实例令牌和 ACTIVE 状态。旧进程在同一秒留下的心跳不能让候选版本误通过。

### 9.3 恢复标记顺序

更新记录在数据库备份和恢复标记持久化之前保持 `PENDING`。恢复标记可以重新读取后才进入 `APPLYING`，因此断电不会留下既无法恢复、又长期占用活动更新锁的状态。

### 9.4 数据库文件

备份先写入 `.db.partial`，完成 SQLite Online Backup、`PRAGMA integrity_check` 和 `fsync` 后原子改名。恢复后的数据库重新设置运行用户权限，再由非特权用户执行旧版本预检。

### 9.5 目录持久化

原子 JSON 替换、恢复标记删除、待执行控制文件删除和数据库替换都会在 Linux 上同步父目录。这样可防止断电后已经删除的恢复标记重新出现并错误覆盖更新后数据。

### 9.6 独立重试记录

更新包摘要索引不再禁止相同签名包产生新的尝试。失败或自动回退的记录可以通过“重新尝试”创建一条新的 READY 记录；原失败记录保持不变，签名包复制到新尝试的不可变文件名并再次校验摘要。安装确认仍需要管理员密码复验。

普通上传仍会在短暂的 SQLite 写事务内拒绝重复摘要，避免被重复上传占满持久卷。只有密码复验后的“重新尝试”通道可以为同一签名包创建第二条记录。

## 10. 数据迁移

新增 Alembic revision：

```text
0008_scope_paging_update
```

迁移只把 `system_update.package_sha256` 的唯一索引改成普通查询索引，以允许相同签名包保留多次独立尝试。客户、用户和业务历史表没有删除字段或破坏性迁移。

## 12. 验证计划

全部实现完成后统一执行一次：

```powershell
cd backend
..\.venv\Scripts\python.exe -m pytest
cd ..\frontend
npm.cmd test
npm.cmd run build
```

随后迁移现有本地 SQLite，并重新启动 Web、Runner、Scheduler，验证健康检查和页面访问。当前 Windows 开发机没有 Docker CLI，因此 Linux 目录 `fsync`、UID/GID 恢复与容器内真实更新/回退仍需在最终交付前使用目标架构 Docker 副本做断电故障演练，不能用 Windows 单元测试替代。
