# 1.0.3：Linux Runner 权限与功能时区

## 1. 来源与处理原则

本次根据 `C:\Users\ASUS\Downloads\fcc_fixes.zip` 中记录的部署现象，处理以下问题：

1. 带依赖功能使用虚拟环境 Python 时出现 `Permission denied`；
2. 升级前已经创建的环境目录重启后仍然不可访问；
3. `fcc-script` 无法穿越 `/data/tmp/runs` 打开任务引导文件；
4. 功能代码使用 `datetime.now()` 时没有采用平台系统时区；
5. 精简 Linux 镜像缺少 POSIX `TZ` 解析所需的系统时区数据。

外部修复包基于 1.0.0，不能直接覆盖当前源码。尤其不能把共享缓存和任务父目录交给 `fcc-script` 所有：目录所有者具备写入、删除和替换能力，会让一个功能进程影响其他功能。这里保留问题现象，重新按照当前版本的权限边界实现。

## 2. 最终权限模型

| 路径 | 所有者 | 权限 | `fcc-script` 能力 |
|---|---|---:|---|
| `/data/runtime-cache` | `root:root` | `0755` | 只能穿越和查看入口 |
| `/data/runtime-cache/environments` | `root:fcc-script` | `0710` | 只能按已知路径穿越，不能列出或写入 |
| 单个虚拟环境目录 | `root:fcc-script` | `0750` | 可以读取和执行，不能修改 |
| 虚拟环境普通文件 | `root:fcc-script` | `0440` | 只读 |
| 虚拟环境可执行文件 | `root:fcc-script` | `0550` | 只读、可执行 |
| `/data/runtime-cache/wheels` | `root:root` | `0700` | 不可访问 |
| `/data/tmp` | `root:root` | `0711` | 只能穿越 |
| `/data/tmp/runs` | `root:fcc-script` | `0710` | 只能按已知路径穿越，不能列出、创建或删除任务 |
| 单次任务目录 | `fcc-script:fcc-script` | 目录 `0700`、文件 `0600` | 只能访问任务自身材料 |

共享虚拟环境是内容寻址缓存，发布后不需要由功能进程写入。Python 子进程继续使用 `-B`，不会尝试在只读环境中生成 `.pyc`。

## 3. 权限生命周期

新增 `backend/app/infrastructure/runtime_permissions.py`，集中管理运行目录权限，避免 Launcher、依赖准备器和任务物化器各自形成不同规则。

### 3.1 新环境发布

依赖准备仍由 root Runner 完成。`venv` 创建、wheel 下载、安装、`pip check` 和清单写入全部成功后，才递归发布只读权限，随后数据库状态才会进入 `READY`。发布前会确认构建器返回的路径直属受信任的 `runtime-cache/environments`，拒绝对任意外部目录执行 root 权限修改。

### 3.2 历史环境自愈

Launcher 每次启动和数据库恢复后都会修复已有缓存。Runner 自身启动时还会修复 `runtime-cache`、`tmp` 和 `tmp/runs`，保证通过旧 Launcher 安装 1.0.3 更新包时，无需额外重启容器就能修复历史目录及全部穿越链路。

环境根目录或任务父目录如果是符号链接，启动会失败并留下错误，而不是让 root 跟随链接修改工作区外路径。共享环境里的正常 venv 符号链接只调整链接自身归属，不跟随到系统 Python。

### 3.3 任务目录

Launcher 预先建立 `runs` 父目录，`RunMaterializer` 在每次执行前再次核对。父目录保持 root 所有，只给 `fcc-script` 组一个执行位。具体任务目录仍由 Runner 创建，内容写完后递归交给 `fcc-script`，任务结束后由 root Runner 清理。

## 4. 功能进程时区

Runner 每次启动功能进程时读取当前 `system.timezone`，通过最小环境中的 `TZ` 传入。这个值已经由后台保存逻辑使用 `ZoneInfo` 校验，只接受有效 IANA 名称。

例如后台选择 `Asia/Hong_Kong` 时，功能代码中的 `datetime.now()` 会使用对应本地时间。管理员以后切换到其他时区，新启动的任务自动采用新值，不要求修改 Compose 或功能包。

平台服务和 JSONL 程序日志继续以 UTC 为稳定基线。没有在 `docker-compose.yml` 写死 `Asia/Shanghai`，避免 Docker 和后台出现两个互相冲突的时区配置来源。

## 5. 镜像

正式镜像安装 Debian `tzdata`，同时保留 Python 项目固定的 `tzdata==2026.3`：

- Python `ZoneInfo` 在开发机和镜像中都有 IANA 数据；
- POSIX 子进程收到 `TZ=区域/城市` 后也能由 C 运行时正确解析；
- 容器默认显式为 `UTC`，功能进程按后台设置覆盖。

这没有增加新服务，也没有增加甲方部署时需要填写的环境变量。

## 6. 验证覆盖

新增自动化覆盖：

- 共享环境始终由 root 持有，组权限中没有写位；
- wheel 缓存保持 root 私有；
- `runs` 父目录只有组穿越权限；
- 顶层符号链接和构建器越界路径被拒绝；
- 普通文件与可执行文件发布模式正确；
- 子进程环境使用传入的平台时区，不继承宿主 `TZ`；
- Linux root 且存在 `fcc-script` 时执行真实身份测试：可以执行共享环境程序和读取模块，但不能修改环境、写任务父目录或读取 wheel 缓存。

当前 Windows 开发机没有 Docker CLI，也没有可用的 WSL Linux 发行版。因此 Linux 真实 UID/GID 测试会在本机明确跳过，必须在交付镜像构建机执行同一测试后才可签署镜像级验收。

本次完成后的统一验证结果：

- 后端：`56 passed, 1 skipped`，唯一跳过项是要求 Linux root 和 `fcc-script` 真实账户的正反向权限测试；
- 前端：4 个测试文件、9 项测试全部通过；
- 前端生产构建：通过，4719 个模块完成转换；Vite 仍提示既有主包超过 500 kB，这是性能优化提醒，不影响本次权限与时区修复；

由于本机没有 Docker CLI，本次不能把“Docker 镜像构建成功”和“Linux UID/GID 实测成功”写成已通过。这两项继续作为正式出包前的阻断性验收门槛，而不是以 Windows 模拟结果替代。
