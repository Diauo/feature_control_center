# 1.0.2：任务结束后的实时日志页面失去响应

## 1. 现象

任务正常结束或主动停止后，运行详情页可能长时间没有响应，返回运行记录、切换菜单等操作也会被阻塞。问题与 Runner 是否正确写入终态无关，日志和最终状态在 SQLite 中已经完整封存。

## 2. 复现与定位

先使用每 0.3 秒输出一条日志的测试功能完成了两条真实运行：

- 正常结束：状态进入 `SUCCEEDED`，最终事件序号正确；
- 运行中停止：状态进入 `STOPPED`，停止后的事件序列不再增长。

100 条日志不足以稳定触发现象。随后在隔离数据目录中构造 10,000 条连续事件，并让运行详情通过 SSE 从第 500 条继续追赶。旧页面在 10 秒内无法完成浏览器运行时查询，确认卡顿发生在前端日志消费阶段。

根因在 `RunDetailView.vue` 原有的逐条处理：

1. 每收到一条 SSE 事件，都重新遍历全部已显示日志并创建 `Set`；
2. 每条事件都对完整数组重新排序；
3. 每条事件都安排一次 DOM 高度读取和滚动；
4. 页面没有可见日志上限，长任务会持续增加 Vue 节点和浏览器布局成本；
5. 任务结束前，SSE 会快速补齐数据库中最后一批日志，因此上述成本集中出现在“正常结束”或“主动停止”的时点。

这是一条随日志数量放大的前端复杂度问题，不是给终态处理增加延时或刷新页面能够解决的问题。

## 3. 修改内容

### 3.1 有界日志缓冲

新增 `frontend/src/lib/runEventBuffer.ts`：

- 用单调事件游标去重，不再为每条日志遍历现有数组；
- 一个接收批次只排序一次；
- 运行详情最多保留最近 2,000 条可见日志；
- 记录被省略的条数，并在控制台顶部明确说明；
- 页面限制只作用于浏览器 DOM，不删除数据库日志，也不改变 `.log`、`.jsonl` 下载内容。

2,000 条约等于测试功能以 0.3 秒间隔连续输出 10 分钟的记录。这个窗口足以观察当前执行，同时避免把浏览器当作无限日志存储器。

### 3.2 合并实时更新

SSE 日志先进入短队列，每 50 毫秒合并写入 Vue 状态。终态事件到达时会先同步清空待显示队列，再关闭连接并刷新运行摘要。这样既不会丢失终态前的最后一批日志，也不会为集中到达的每条事件分别重绘页面。

自动滚动最多在下一帧执行一次。组件退出时会关闭 SSE，并清理日志提交计时器和滚动帧。

### 3.3 历史任务只读取尾部

打开已有任务时，根据 `latestSequence` 从最近 2,000 条附近开始读取。接口单页仍保持 500 条上限，其余尾部记录由原有 SSE 游标协议补齐；终态任务补齐后会收到 `run` 事件并正常关闭连接。

### 3.4 测试功能包

新增 `examples/feature-packages/log_stream_test`：

- 默认输出 100 条日志；
- 固定每 0.3 秒输出一次；
- 每轮检查 `ctx.raise_if_cancelled()`；
- 日志包含序号、总数、进度和已运行时间；
- 不访问网络、不使用数据源、没有第三方依赖。

开发环境中可直接上传的文件：

`dist/test-packages/实时日志稳定性测试.zip`

后续正式制作交付包时，构建脚本会自动生成：

`feature-packages/实时日志稳定性测试-<版本>.zip`

本次按要求没有重新制作桌面交付 ZIP。

## 4. 回归覆盖

新增前端测试：

- 乱序批次排序和重复事件过滤；
- 10,000 条集中追赶后只保留序号 8,001～10,000；
- 从尾部加载时正确计算已省略数量；
- 2,100 条 SSE 日志加终态事件只触发一次有界渲染，连接关闭后仍能返回运行记录。

验证结果：

- 后端：`48 passed`；
- 前端：`4` 个测试文件、`9 passed`；
- TypeScript 与 Vite 生产构建：通过；
- 10,000 条隔离复现：页面显示最近 `2,000` 条、已省略 `8,000` 条、最终序号 `10,000`，状态为“日志已封存”；
- 完成追赶后点击“返回记录”约 `425 ms` 完成导航，浏览器保持响应。

Vite 仍提示主 JavaScript 包超过 500 kB。这是既有的拆包优化项，与本次页面冻结无关，不影响构建通过。

## 6. 边界

- 平台仍然保存保留期内的全部执行日志；
- 平台没有增加商品、失败项识别或业务重试；
- 2,000 条是浏览器可见窗口，不是日志保存上限；
- 测试功能只验证 Runner、实时日志、正常结束和主动停止，不代表任何库存同步业务验收。
