# 0.0.4 — 明确登录 Token 和会话安全机制

## 日期

2026-09-08

## 问题

`0.0.3` 完整方案已经提到 Argon2id、服务端会话、安全 Cookie、CSRF 和会话吊销，但没有把登录 Token 的生成、存储、传输、校验、过期和即时失效流程写成可直接实现的协议，容易让开发阶段重新退回到旧系统的长期 JWT 和浏览器 `localStorage` 模式。

## 决策

1. 浏览器登录采用 256 位随机不透明会话 Token，不使用长期 JWT。
2. 原始 Token 只存在于浏览器 Cookie，SQLite 只保存 HMAC-SHA-256 摘要。
3. 公网 HTTPS 使用 `__Host-fcc_session`、`Secure`、`HttpOnly`、`SameSite=Lax` 和 `Path=/`，不设置 `Domain`。
4. 前端不得将 Token 放入 `localStorage`、`sessionStorage` 或状态持久化。
5. 用户、角色和客户权限保存在服务端并按请求校验，不编码进 Token。
6. 密码重置、角色变化、用户停用和强制下线立即吊销现有会话；客户关联移除通过实时授权立即生效。
7. 推荐默认闲置超时 2 小时、绝对有效期 12 小时、敏感操作重新认证 10 分钟，不提供永久“记住我”。
8. 修改接口必须通过会话绑定的 CSRF Token 和来源校验。
9. 登录防爆破使用账号和 IP 双维度分级冷却，不增加图片验证码或永久锁定。
10. 首版不强制 MFA，不创建第三方 API Token；两者保留清楚的扩展边界。

## 变更边界

- 本次只修改方案和版本文档，没有实现认证代码。
- 没有修改 `features/` 原始功能素材。
- 没有引入 Redis、OAuth 服务、短信服务、验证码服务或外部身份提供商。
